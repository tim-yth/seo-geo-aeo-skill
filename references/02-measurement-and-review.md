# 02 · 量測與驗收：基準、比較窗、指標與因果判斷

> 案例站（繁中塔羅占卜工具站）第一波改版後，改過的頁點擊 +46～58%，看起來很成功。
> - 加上對照組（同頁群裡沒改的頁），扣掉前窗一頁 7 天的外部爆量後，淨效果是 −1.1%（p=0.91）。沒扣之前是 −35.2%：同一個 DiD，被一段爆量放大成「大退步」（步驟 3 第 8 點）。
> - 把上線日往前移兩週再算一次（安慰劑檢驗；當時是 14 對 14 的頁級窗），反而得到 +60.7%（p<0.001）。也就是說，改版前就已經在漲。本章的 28 天窗要往前移 30 天（步驟 3 第 9 點）。
>
> 這一章教你怎麼取數字、怎麼比較、怎麼證明「是我們做的」：不把運氣記成功勞，也不把外部波動誤判成自己闖的禍。

## 何時使用

- 任何一波改動到了驗收日（`review-due.mjs` 列為 due 或 overdue）。
- 使用者問「上次改的有沒有效」「流量為什麼掉了／漲了」「這半年哪一版最有效」（步驟 4b）。
- 寫任何含數字的報告之前：期中、正式、週報、下滑調查都算。
- 要新增指標、改舊門檻、換資料口徑時。先讀步驟 8 的「口徑漂移」規則。
- 要回答「搜尋進來的人有沒有開始用」：口徑在步驟 3 第 14 點與步驟 6，做法與門檻在 `17`。

## 步驟

### 步驟 1：先確認資料能用

每份報告的第一段都要寫這些。

1. **只用定稿（final）資料下決定。**
   - GSC 最後 2–4 天是暫定值，事後會改。案例中某日點擊從 221 改成 227，某頁單日從 20 改成 53。
   - `gsc-export` 和 `gsc-compare` 預設只用到最新的定稿日。
   - 用 `--data-state all` 時，回應裡 `firstIncompleteDate` 及之後的日子都是暫定，只能當預警。
   - 哪幾天已定稿要驗證，不要只靠推估：同一段日期用 `final` 和 `all` 各抓一次逐日比對，差異為 0 的日子才算定稿（案例比對 58 天，0 差異）。
2. **寫明三個時鐘。**
   - GSC 以 PT（美西時間）切日。
   - GA4 用屬性時區。一定要先查：案例是 UTC+10，不是營運地時區。
   - 部署紀錄用網站時區（`config.site.timezone`）。
3. **部署日整天排除。**
   - 部署當天（網站時區）所涵蓋的 PT 日都是新舊混合日，比較時整天排除。
   - 在 UTC+8 部署，當地一天會跨到兩個 PT 日，兩天都要排除。
   - `gsc-compare --deploy-date` 會自動排除。
4. **驗收用的匯出必須能證明自己完整。**
   - 要符合三件事：日期範圍等於目標窗；每日資料的最後一天 ≥ 窗末；產生時間 ≥ 窗末＋2 天。
   - 案例中有一份舊匯出，檔頭寫到 10/05，實際資料只到 09/19，第一版驗收器照單全收。
   - 正式驗收一律重新匯出，不重用期中的檔案。
5. **資料成熟時間。**
   - GSC：窗末後約 3 天定稿，`review-due` 依此排驗收日。
   - GA4：部署後第一個完整日，要到 D0+2 才看；7 日窗要到 D0+8 才成熟，28 日窗要到 D0+29。日表在 72 小時內可能被改寫。
   - CrUX：每個資料點是 28 天滾動。CrUX API 每天更新（落後約 2 天），History API 每週一更新；BigQuery 月表在次月第二個星期二發布（查證日 2026-11-02）。效能改動多久能驗收，見 `16` 第 6 節。
6. **日曆到了，不代表資料齊了。**
   - D+14 當天，定稿資料只到約 D+11。
   - 兩種做法擇一：兩個窗同步縮短（`gsc-compare --allow-partial`），或晚 2–3 天再判。
   - 報告裡寫明選了哪一種。
7. **窗長自己算，不信檔名與文字。**
   - 窗長＝含頭尾的日曆天數。案例檔名寫「90d」的基準實際是 92 天；另一份方案寫「09/24 到 10/07 前一日」其實只有 13 天。
   - 發現不等長時不要靜默改基準：原版照算（比日均），另附一個等長、星期組成相同的版本並列。
   - 還沒定稿的日子是「缺」，不是「0」，不能補 0 再平均。
8. **先查 GSC 資料本身有沒有官方公告的異常。**
   - GSC 官方「資料異常」頁公告：**2025-05-13～2026-04-27 的曝光記錄有誤，CTR 與平均排名也受影響，只有點擊不受影響**。比較窗（含 `--yoy` 的去年窗）任一端碰到這段，曝光、CTR、名次的變化一律標「不可判讀」，結論只用點擊。官方沒有說明這段會不會回補（查證日 2026-11-02）。
   - 同一頁還公告過：2026-02-28、03-01 部分資源的 BigQuery 大量匯出整天缺漏、不會補回；2026-08-13～17 生成式 AI 曝光短少（已補回）；以及多次 Discover 記錄問題。
   - 完整的外部事件帳本（Google 更新＋資料異常）見步驟 4。

### 步驟 2：選比較窗

| 窗型 | 怎麼取 | 用途 | 依本規則取窗的例子（案例日期） |
|---|---|---|---|
| 正式 28 對 28 | 部署日後 28 天對部署日前 28 天（排除部署日涵蓋的 PT 日） | D+28 正式判定 | 台北 10/07 凌晨部署，PT 10/06、10/07 兩天都排除 → 後窗 10/08–11/04，前窗 09/08–10/05 |
| 期中 14 對 14 | 同上，取 14 天 | D+14 看方向 | 10/08–10/21 對 09/22–10/05 |
| 7 對 7 | 同上，取 7 天 | D+7 看風險與方向，不下結論 | — |
| 避開異常日 | 異常前後各挑一段乾淨的 7 天（或 7 的倍數） | 有爆量時的主結論 | 09/27–10/03 對 10/15–10/21 |
| 對照組 | 與處理組完全同一組窗 | 算淨效果 | 見步驟 3 第 8 點 |
| 安慰劑 | 只用上線前的資料，假裝提早上線 | 檢查改版前的既有趨勢 | 第一波安慰劑 +60.7%（14 對 14 頁級窗，往前移兩週） |
| 季節性 | 同一組窗往前 364 天（星期對齊） | 排除季節因素 | `--yoy` |
| 外部事件 | Google 更新前後各 14 天；後窗排除更新進行中的日子 | 判斷外部影響 | 核心更新 +178% |

案例當時實際用的前窗是 09/09–10/06（期中 09/23–10/06）：只排除了台北日期 10/07，PT 10/06 其實含約半天新版。上表是照本規則該取的窗，不要重蹈覆轍。

規則：
- **等長、完整日、星期組成相同。**
  - 窗長是 7 的倍數時，星期自動對齊。
  - 其他長度時，`gsc-compare` 會把前窗往前推，讓兩窗從同一個星期幾開始。`--no-align-weekday` 可關閉這個行為，但除非有理由，不要關。
- **窗長不同時，只比日均。** 日均＝總量 ÷ 窗口的日曆天數，不是除以 API 有回傳的列數。
- **重疊的期中結果不能串成趨勢。** 起點不同、互相重疊的 +2.3%、+4.2%、+7.2%，不是三個獨立樣本，不能畫成「成長在加速」。
- **要畫趨勢，用不重疊的週表。** 週一到週日為一格（或不重疊、星期組成相同的 4 週塊），連續排開，每一格標上當週的部署與外部事件。案例的週表一眼就看出：有效點擊在部署前一週已經到 1,219，之後四週是 1,140、1,259、1,091、1,212。回升在改版前就完成，改版後是持平，不是「一版比一版高」。
- **前窗不要跨過外部斷點。** 改動如果是在 Google 整群重排或核心更新之後上線，前窗要從斷點之後開始。寧可縮成同星期組成的 2–3 天，也不要拿重排前的數字當基準。
- **產品改動的前窗要「規則一致」**：前窗裡不能夾著別的實驗收尾或規則切換。原訂前窗不乾淨時，往前挪一週當主版，原訂窗當敏感度檢查。
- **避開異常日要連尾巴一起避開。** 爆量結束後還有幾天高於平常（案例平常每天約 165 次點擊，結束後兩天還有 253、232）。再把基準換成相鄰的另一週重算一次，結論相同才採用（案例 +3.8% 變 +6.5%，都判持平）。
- **後窗拆成前半、後半各看一次。** 案例的首頁扣掉品牌字後，點擊 71→232，但 185 次落在前 7 天、後 7 天只剩 47，所以判「窗內達成但未維持」。
- **回頭驗收被後續改動蓋過的波次：每頁各取一個「乾淨的最長等長窗」。** 後窗止於這頁下一次被改（title、內文、連結）或碰到爆量的前一天；前窗取同樣長度、同樣星期組成。乾淨後窗不到 7 天，就判「無法判斷（被後續改動汙染）」，不要硬算。
- **每個版本各算一次同查詢 CTR。** 固定查詢集合含爆量查詢時，同查詢 CTR 一樣會被扭曲（案例原窗 5.26%→6.62%，乾淨週 1.82%→1.89%）。
- 例（非占卜站）：手沖咖啡教學站週一上線新版「手沖比例計算器」。28 天窗的前窗和後窗都從週二開始，各含 4 個週末；比較用的是週二到下週一，不是「上個月」對「這個月」。

### 步驟 3：跑比較，依序拆解

```bash
# 波次已用 log-change 登記：讀它的日期、網址、護欄
node scripts/gsc-compare.mjs --wave <波次id> --checkpoint D+28 --placebo-shift 30 --yoy --by searchAppearance,device
# 沒登記：直接給部署日與改過的網址
node scripts/gsc-compare.mjs --deploy-date 2026-10-07 --window 28 --urls-file .seo-agent/data/treated.txt \
  --placebo-shift 30 --target-query "<核心字>"
```

照下面順序做。每一項在案例中都改變過結論。

1. **重現舊基準。**
   - 用新匯出重算上一份報告的基準數字，一致才往下做。
   - 不一致時，先查口徑：篩選、時區、匿名查詢、是否定稿。不要直接拿來比。

2. **全站四指標＋點擊拆解。**
   - `gsc-compare` 把點擊變化拆成三塊，三塊相加等於總變化：
     - 曝光效果：需求或能見度的變化。
     - 名次效果：依 CTR 曲線換算名次變動的影響。
     - 同名次 CTR 效果：搜尋摘要、SERP 版面、意圖的變化。
   - 這是模型歸因，不是因果證明。腳本不能用時，照「手算公式」用中點法拆兩塊。
   - 案例：7–8 月點擊 −22.7%（少了 982 次），拆開後幾乎全是曝光消失（曝光效果 −990，CTR 效果 +8）。再看子市場 hub 在子市場主字上的逐週曝光：1,005→707→52→0→0→1→1,399。整頁掉出搜尋結果 4 週後又回來，平均名次完全看不出來；子市場相關頁（hub＋子市場文章）合計占這次下滑的 53%。

3. **全站 CTR 下滑時，先算同查詢 CTR。**
   - 取兩期各有 ≥50 曝光的查詢，用前期曝光當權重算後期 CTR。公式見「決策規則」。
   - `gsc-compare` 會自動算出全站與各查詢群的同查詢 CTR。門檻用 `--min-impr` 調整；另外以 25 跑一次，當敏感度檢查。
   - 案例：全站 CTR 2.72%→2.39%，同查詢 CTR 卻是 1.80%→2.12%。是新增的低點擊曝光把平均稀釋了，不是變差。
   - 再做一個敏感度版本：扣掉「整窗 0 點擊且曝光 ≥100」的查詢，再算全站 CTR，和同查詢 CTR 一起報。案例另一次期中，同查詢 CTR 1.93%→2.14% 在升；扣掉高曝光零點擊查詢後，全站 CTR 是 3.00%→2.49%，仍在降，代表還有一部分是組成變化（新進的中排名字），不全是垃圾曝光。

4. **有異常就並列多個版本，以最乾淨的為主結論。**
   - 版本至少有：原窗、扣掉異常查詢、避開異常日。
   - 案例的期中驗收：

     | 版本 | 結果 |
     |---|---|
     | 原窗 | +22.7% |
     | 只差一天的字面窗 | −2.4% |
     | 扣掉爆量查詢 | +15.4% |
     | 避開爆量日 | +4.7%（同查詢 CTR 1.82%→1.89%） |

     最後判為「持平」。只差一天正負號就翻轉，代表原窗不穩。
   - **「扣異常查詢」版本＝總數減去異常查詢，不要用查詢層加總。**
     1. 從匯出資料裡逐條列出異常查詢，不要只寫一條 regex 就算完：品牌名的各種拼法、簡繁、錯字、對方網域、外語寫法都要找出來確認。案例為了一次他站品牌爆量列了 85 條。清單和 regex 一起存檔。
     2. 扣除版＝頁面層（或全站）總數 − 這些查詢的點擊與曝光。總數裡保留匿名查詢；直接把「查詢×頁面」匯出排除後再加總，匿名查詢會整個消失，就不能和其他版本比。`gsc-compare --exclude-query` 就是這樣算的。
     3. 扣除後的平均名次只是近似值，報告要註明。
     4. 扣完仍偏高，代表爆量也帶動了一般字和匿名長尾（案例扣掉品牌字後，爆量週每天仍有 250–400 次點擊，平常約 165）。這時以「避開異常日」版本為主結論。
   - **名字要寫對。** 只看查詢層的扣除數字，是「排除這組查詢模式後，GSC 有回傳查詢字的曝光」，不是「排除異常後的全部曝光」：匿名查詢沒辦法排除，也沒辦法還原。也不要用「頁面總數 − 這個數字」，把差額全算成異常流量。案例的首頁：排除後的可見查詢日均 257.6→18（−93.0%），只能證明異常解釋不了全部下滑，不能拿來算異常占了多少。
   - **截斷乾淨版**：下一波在本波後窗內上線時，把後窗截到下一波 D0 的前一天（不等長就比日均），當成另一個版本並列。樣本小，只看方向，但能告訴你「整體方案效果」裡有多少屬於本波。案例第二波：8 天後窗（混了兩波）清洗後 +7.7%（p=0.65），截到下一波之前的 5 天乾淨版是 −0.9%。

5. **辨識異常。** 每一項都列「含／不含」兩個版本，保留原值；不能事後把頁刪掉，再宣告成功。
   - **導航型爆量**
     - 特徵：曝光只多 2–3 倍，CTR 卻從 <1% 跳到約 30%，名次不變。這是有人在搜某個品牌名（通常是社群帶起來的），不是你的排名上升。
     - 它也會帶高相關的一般字和匿名長尾，所以要整段避開那幾天，只扣掉品牌字不夠。
     - 案例：週點擊變 4.3 倍，一夜之間結束。
   - **異常基準**
     - 特徵：基準期的點擊集中在少數幾天；同樣曝光下 CTR 從常態跳高，名次反而變差。這是外部事件，之後歸零不算流失。
     - 案例：176 次點擊裡有 166 次落在 7 天內，CTR 從常態 0.1–0.3% 跳到 8–16%。
   - **無關長查詢**
     - 特徵：單一查詢有數千次曝光、0 點擊，多半是另一種文字或語系的長句（案例是簡體長句）。
     - 判定規則（寫進口徑，之後每次比較照用）：整段資料期 0 點擊，**而且**語系不符（案例：經簡轉繁工具轉換後字會變＝含簡體字），**而且**去空白後 ≥8 字，或總曝光 ≥1,000。短查詢（<8 字）多半是真人只是沒點，列出但不扣。
     - 案例：165 個查詢、約 3 萬次曝光；其中一條在一篇文章上灌了 4,272 次曝光。某個月全站曝光有 8.8% 是這類長查詢，加上他站導航字共 14.9%；在文章頁群裡兩者合計占 25.5%。扣掉後文章 CTR 是 2.79%，帳面只有 2.08%。
     - 這類曝光改文章修不好，只能在判讀時扣掉。
     - 扣除只扣得到看得見的查詢：匿名查詢裡的同類流量扣不掉。另做一個「下界版」：把主要承接這類流量的頁整頁扣掉（含匿名查詢）。兩版差距很小，結論才算穩（案例月點擊 5,056 對 5,043）。
   - **單頁異常**
     - 特徵：一週點擊變成 20 倍，名次和曝光都不動。先不認列；用 GA4 同期的自然 session、互動時間、來源核對（`templates/review-report.md` 第 6.1 節）。
   - **只曝光、不點擊的桌機流量**
     - 特徵：某頁桌機占約四成曝光、幾乎沒有點擊，之後某天整批消失，名次不變。比較像自動查排名的工具，不是真人需求（推測）。
     - 案例：一頁桌機 2,319 次曝光只有 1 次點擊；這批消失是該頁曝光下滑的一部分原因，但同期手機曝光也在掉，所以不是全部。
     - 判讀曝光下滑之前，先分裝置看是不是只有這類流量不見了。
   - **需求波動**
     - 特徵：名次幾乎不動，曝光卻大起大落。
     - 案例：子市場主字的主頁名次一直在 7.6–9.2，每週曝光卻從 7 次到 2,116 次不等。
     - 這是需求變化，不是排名變化，原因多半在站外（季節、社群、他站事件）。不要拿這種波動判斷 SEO 改動成不成功，改用名次相近的日子比較。
   - **每個目標頁先列查詢組成，再下單頁判定。** 報告逐頁列出比較期前 5 大查詢，並標「自家意圖／他站品牌／無關長查詢」。案例早期的自動驗收器只看「點擊和曝光有沒有同時下滑」：一篇吃到他站品牌爆量的文章被判「延續」，一篇 85% 曝光（4,272／5,034）來自一條無關長查詢的文章也被判「延續」，一篇只是回到常態的文章反而被判「重新診斷」。哪些查詢算「相關」要在上線前登記（`templates/wave-record.md` 第 3 節），事後才決定，就是在挑對自己有利的字。
   - 例（非占卜站）：食譜站的一道菜被電視節目介紹，三天內那道菜的查詢 CTR 暴增。這不是你的 title 改得好。

6. **品牌與非品牌分開看。**
   - 查詢分三類：自家品牌字（`config.site.brandTerms`）、他站導航字（用 `--query-group` 定義）、一般字。
   - 案例：首頁曝光漲了 4.4 倍，其中 76.5% 是他站導航字。
   - 付費廣告上線或暫停時，要看品牌字有沒有被帶起來。
   - GSC 介面的品牌查詢篩選（2026-03 起對符合資格的網站開放）可以拿來交叉檢查你的 `brandTerms`；驗收數字仍以 API 匯出為準。

7. **比較頁群與查詢群。**
   - 頁群用 `config.pageGroups` 定義（首頁、工具、文章、hub…）。
   - 查詢群用 `config.queryGroups` 或 `--query-group` 定義（意圖群、子市場）。
   - 漲跌以頁面層為準，因為頁面層包含匿名查詢；查詢層只看方向。案例中，查詢層只涵蓋頁面點擊的 10%～38%。
   - **查詢層的涵蓋率會逐月變，查詢層趨勢會偏樂觀。** 案例的可見查詢，從占頁面點擊的 10%（剛上線那個月）升到 38%，所以「某組查詢半年成長 5 倍」有一部分只是看得見的變多了。跨月比較查詢層時，同時列出當月涵蓋率（可見查詢點擊 ÷ 頁面層點擊）。案例早期也算過「匿名曝光 91%→55%」，但剛上線那幾個月落在 GSC 曝光記錄錯誤期（步驟 1 第 8 點），曝光類的比例只當參考，點擊涵蓋率不受影響。
   - **頁群比較用固定的頁集合。** 主結論只用「兩個窗都已經有曝光」的頁，新頁另列。新頁沒有前期可比，改用「上線到第一次曝光幾天、第 4 週每日曝光」另外驗收，不放進 DiD。案例：全部文章 90 天點擊 +59%；只看前窗已有曝光的 595 篇是 +42%。差額來自新文章，剩下的 +42% 也不是改版成果，而是同一批文章上線 2–3 個月內本來就還在爬升。

8. **處理組對照組（差異中之差異，DiD）。**
   - 指定改過的頁：
     - 用 `--urls` 或 `--urls-file` 列網址，對照組自動取同頁群裡沒改的頁。
     - 或用 `--treatment <regex>` 篩處理組、`--control <regex>` 篩對照組。
     - 對照組怎麼選（含同模板大量頁的隨機分組）見 `03` 步驟 1。
   - 看淨效果，不看處理組自己的前後比。
     - 算法：`gsc-compare` 用每日的 log((處理組點擊＋1)÷(對照組點擊＋1))，以後窗平均減前窗平均，淨效果＝e^差值 − 1。
     - p 值用前窗／後窗標籤的置換檢定。窗口 ≥14 天且是 7 的倍數時，以整週為單位置換，保留每週的季節性。
   - **DiD 也要多版本。** 處理組或對照組的前窗裡只要有一段外部爆量，DiD 就會被放大或翻向。案例第一波：原始版 −35.2%（p<0.001），因為處理組前窗有一頁 7 天的外部爆量；扣掉這段與一條無關長查詢後是 −1.1%（p=0.91）；再扣全部導航字是 −1.6%（p=0.84）。三版並列，以最乾淨的為主結論。
   - **報告寫明用的是哪一種檢定。** 案例當時用條件二項檢定（就是「決策規則」裡的手算 DiD）；本 skill 的 `gsc-compare` 用每日 log 比值加置換檢定。兩者對單日爆量的敏感度不同，數字不必完全一樣，但結論方向要一致。
   - 案例一：15 張改了 title 的牌義頁 +10%，其餘 63 張 −28%。**這只是 D+7、只能看方向、信心低的結果**：每日約 3 次點擊，CTR 0.74%→0.58%；而且只有換成「扣掉爆量」的前窗才有這個差，用原訂前窗是 −10% 對 −11%，幾乎沒差。兩個前窗並列，等 D+28 定案。
   - 案例二：8 張改了 title 的另一牌種頁 −31%，對照組 +23%。原因是其中一頁不再對上離題字，而離題流量也是流量。
   - 最乾淨的對照：兩組都受到同一個全站改動，差別只剩被測的欄位。
   - 對照組不能被其他波次碰過，用 `log-change.mjs list` 查。

9. **安慰劑檢驗。**
   - 做法：加上 `--placebo-shift <天數>`。它會把兩個窗整段往前移這麼多天，用同一組處理組與對照組再跑一次。
   - 天數至少要是「窗長＋被排除的部署日數」，安慰劑的後窗才不會碰到真實部署日。網站在 UTC+8 這類時區時，一個當地日會跨兩個 PT 日，所以 28 天窗要用 30。報告若出現「placebo post window overlaps the real deploy」，就把天數加大。
   - 判讀：安慰劑和真實結果同方向，而且量級至少是真實結果的一半，或同方向且安慰劑 p<0.1，就代表那是既有趨勢，不認列。`gsc-compare` 的報告會直接標出來。
   - 案例的第一波：真實淨效果 −1.1%，安慰劑 +60.7%。實驗組在上線前兩週，就已經比對照組多漲了六成。當時是 14 對 14 的頁級窗、往前移兩週；不要拿 14 天的位移去配 28 天的窗。

10. **名次要用三個替代指標看，不能只看平均名次**（原因見「常見錯誤」第 4 條）。
    - **固定集合位移**：取前期曝光 ≥10 的（查詢, 網址）組合，用前期曝光加權看名次變化；後期消失的組合另外列出。`gsc-compare` 的 fixed-set 段會依前期名次分成 1–3／4–6／7–10／11–20／21+ 五個桶。
    - **前 10 名天數**：窗內「平均名次 ≤10.5 且曝光 ≥5」的天數。只能叫這個名字，不能叫「第一頁天數」。`gsc-compare --target-query "<字>"` 會列出前後窗的天數；護欄查詢一律會列。
    - **邊界曝光占比**：排在第 8.5–10.5 名的曝光，占當日總曝光的比例。這個比例下降，常是快掉出前 10 名的前兆（案例 38.2%→20.5%）。用 `gsc-export --dimensions date,query --query "<字>"` 取逐日資料計算。

11. **排名網址與互搶。**
    - 承接比例＝目標頁在該查詢的曝光 ÷ 同一張「查詢×網址」表裡所有網址的曝光。低於 90% 就查互搶。
    - 逐日記下勝方網址和切換次數，用 `query-clusters`。
    - 案例：首頁與工具頁的 title＋H1 一字不差，一組字在 79 天內換了 21 次排名網址。

12. **301 合併與承接轉移。**
    - 新舊網址合計看（案例 283→299）；舊網址歸零是預期內的事。再用意圖查詢群驗收（案例的問法群點擊約 +40%）。
    - **目標頁會繼承舊頁的離題查詢。** 舊頁原本在接的他站品牌字或離題字，301 之後會算到目標頁，把目標頁的 CTR 和名次一起拉低。轉址前先列出舊頁的前 20 個查詢，把不屬於目標頁意圖的寫進目標頁的排除清單，之後看目標頁一律用扣除版。案例一篇在接他站品牌字的文章 301 到子市場 hub 後，每天約 400–450 次、CTR 約 0.4% 的品牌字曝光落到 hub；扣掉後，hub 在乾淨週的曝光其實減半（5,555→2,514）。
    - **舊網址的曝光會拖 1–2 週。** 案例 301 上線後第 6–12 天，舊網址仍記了約 3,700–4,200 次曝光（@5.3–5.4）。這不代表轉址沒生效：先用 `curl -sI` 確認 301 與 Location，再用 URL Inspection 看舊網址狀態；判讀一律新舊合計。
    - **沒有 301、只靠內鏈或 title 轉移承接時，也要合計看。** 刻意把一組查詢從文章轉給 hub 後，文章頁群的曝光下降是預期的；驗收用「hub＋原本承接的文章」在這組查詢上的合計，和非目標查詢分開看。反過來，hub 漲了也不一定是新增需求，先確認是不是從站內別頁搬過來的。案例：內鏈批次上線兩天後，文章頁群比上週同星期少了 22% 曝光，名次持平；可見部分主要是子市場查詢轉到 hub（刻意的效果），加上爆量期跟著來的字自然消退。驗收時寫成「承接轉移」，不寫成文章退步。
    - **年度交棒不算流失**：新年度頁上線後，上一年度同主題頁的流量下滑是預期（案例上一年度運勢文每日曝光 3.5→1.0），不放進流失名單（做法見 `06` 的年度頁規則）。

13. **索引。**
    - `indexing.mjs inspect` 看 Google 選的 canonical 和最後檢索時間。
    - 最後檢索早於部署，代表 Google 還沒看到新版，不能判。

14. **SEO→產品（搜尋落地轉換）。** 做法、門檻與報告格式在 `17`，量的口徑在這裡：
    - **只算自然搜尋的 session**，而且要「同一個 session、落地之後」發生才算轉換。用 BigQuery 以 `user_pseudo_id`＋`ga_session_id` 串接；來源用 session 層級的口徑（A／B 兩種，見步驟 6），不用「首次使用者來源」。
    - **按入口類型分開算**：工具頁、首頁、hub、文章、實體頁（牌義、商品、詞條）各一列，每列寫「落地 → 開始 → 拿到結果 → 完成主要動作」的每落地 session 比率。不能用全站平均宣告成功或失敗。
    - **低互動來源另列**：例如異常國家＋桌機＋Direct，會把全來源平均拉垮。案例 CTA 深連結那一波，全來源的內容頁輸入率 10.2%→8.6%，看起來失敗；只看自然搜尋 session 是 25.0%→26.7%，拿到完整結果 48→70。同期某國桌機 Direct 從 1,436 個 session 漲到 2,183，有輸入的只有 2→0 個。
    - 註冊數、預覽數和流量同幅下降時，是流量問題，不是轉換變差。
    - 「完成」用一組事件的聯集定義（例：完成、登入後解鎖、回站恢復），去重後要求發生在前一步之後。新增事件時，先用舊的事件組合重跑一次，確認差異不是因為多算了新事件。
    - **轉換貢獻表**（每月或每波）：每個落地頁群列「自然 session 占比｜開始占比｜開始率」。兩個占比差很多的頁群，就是搜尋落地轉換要先修的地方。案例某一期：文章占自然 session 47%，只占開始的 18%。
    - **流量上升、轉換不升**：下一波做頁面體驗與 CTA（第一屏入口、CTA 路由、載入速度），不要加文章。
    - **量測缺口先補**：某頁型沒送落地事件，就不能拿它判 CTA 無效（`01` 第 7 節的案例只有約 9% 的落地帶事件）。

15. **小時資料：只用來排先後，不用來量效果。**
    - **先切段，再看數字。** 段落邊界只用三種時間：部署完成時間、Google 重抓受影響頁的時間（`indexing inspect` 的 lastCrawlTime）、外部事件時間。每段寫「曝光／點擊／加權名次／這段之前已完成的部署」。
    - **跨到部署時間的那個小時整桶排除。** 小時鍵代表一整個小時，09 時那桶的曝光分不出在 09:47 部署之前還是之後。
    - **樣本太小的段不拿來排先後。** 一段只有個位數到二十幾次曝光時只記錄。案例第 1 輪說「下滑早於部署」，依據是一個 8 次曝光的小時（@4.25），第 2 輪被推翻；站得住的是部署前 9 個小時合計 61 次曝光、@4.56。
    - **先量事件前的小時波動。** 案例在事件前一兩天就有「4 次曝光 @4.75」「2 次曝光 @4.5」這種短暫跳動；下滑後同一天內也在 4.0–6.6 之間擺動。落在這個範圍內的單一小時不是台階。
    - **不要寫「從某小時起持續為 0」**，除非之後每個小時真的都是 0。案例宣稱歸零之後，原始小時表仍有零星 1 次曝光（@10、@9）。
    - 小時回應裡的 `firstIncompleteHour` 只代表小時資料；日資料有沒有定稿，仍看日資料的 `firstIncompleteDate`。
    - 小時資料只保留約 10 天，事件一發生就匯出存檔。
    - 切段後先後清楚，也只能排除「比這段晚上線的改動」是起點，不能證明其他改動沒有讓下滑持續或加深。

    | 時段（PT） | 曝光 | 點擊 | 加權名次 | 這段之前已完成的部署／重抓 |
    |---|---|---|---|---|
    | 事件前 3 天（基準） | | | | — |
    | 部署 A 之前 | | | | — |
    | 跨部署 A 的小時 | 排除 | | | |
    | 部署 A 之後、Google 重抓之前 | | | | A |
    | Google 重抓之後 | | | | A＋重抓 |

    例（非占卜站）：SaaS 站週二 14:20 上線新定價頁，「CRM 價格」當天名次變差。14 時那桶排除；00–13 時合計 58 次曝光，名次已從前三天的 3.2 變成 4.4。下滑在部署前就開始，新定價頁不是起點；但它會不會讓之後的下滑加深，要看機制，不能靠時間排除。

### 步驟 4：外部脈絡檢查

判讀任何下滑或暴漲之前，都要先做。

| 2026-09-24～10-08 | 垃圾內容更新 | 另立基準 |

更早的更新查 Google 搜尋排名更新的歷史頁；其他會造成台階的日期（例如 GA4 新增 AI Assistant 管道）見 `15` 的「跨情境的量測陷阱」。

**Trends 與外部時間軸的細節**
- Trends 是抽樣後的相對熱度（0–100），不是搜尋量；低量字會顯示 0。範圍 30 天以上時，日期用 UTC 切，不是當地時間，也不是 GSC 的 PT。
- 抓取當天（還沒結束的那一天）可能不完整，比較前先排除；存檔時記下地區、類別、時間範圍、搜尋類型與抓取時間。
- 先對量級：外部需求的變化要和你看到的跌幅同量級，才算解釋。案例裡 Trends 只少 7–16%（同星期組成重算後；原本用 7 天對 6 天、又含抓取當天，算成 22%／15%），解釋不了首頁大字 −96%～−99.7%。
- 官方更新用 Search Status Dashboard 的事件資料（含開始、結束的 UTC 時間）建時間軸，換算成 PT 和當地時間。把「官方 rollout 期間」「業界未確認的波動日」列成候選日期，回頭對 GSC 逐日資料，看整群查詢是不是同一天一起動。

案例：首頁大字在一般字整群重排（PT 10/18–19）之後幾乎消失：PT 10/08–18 對 10/23–28，三個大字的每日曝光 230.6→9.8（−96%；另一組窗 10/12–18 對 10/19–22 算出 −99.7%，所以一定要寫窗口）。同一天，AI 工具頁的一般字也一起掉；國際版頁群同期持平（每日 196→204 次曝光、名次 7.0）。斷點前後約 37 小時（前約 26.5、後約 10 小時）沒有任何 CI 正式部署，但平台的完整部署清單沒有取得，所以只能寫「沒有 CI 部署」。判定為 Google 端重排加上權威不足，不是頁面出了問題。另外，「他語言版的同類字在進步」是幾天後護欄字下滑期間的觀察，不能拿來支持這一天的判斷：不同事件的證據不要混在一起寫。

### 步驟 4b：版本歸因——「流量變多，是哪一版做的？」

使用者問「哪一版最有效」「成長是不是改版帶來的」時，照這個順序回答，不要只做上線前後比：
1. **月表、週表加註記**：我方上線（D0）、Google 官方更新、GSC 資料異常、量測斷點、廣告開關、外部爆量、外部引用上線。
2. **每一版並列多種窗**：D0 前後各 7 日、前後各 14 日、固定 28 日、連續同星期的 4 週塊。點擊、曝光與名次、轉換三個角度分開判斷（轉換類改動用 `17` 的口徑）。
3. **先排除外部事件**：用官方更新日做前後 14 日比較，同時查那段期間有沒有我方部署；沒有部署，就不是我們做的。
4. **做「成長引擎表」**：各頁群的有效點擊月日均與增量占比（先扣掉他站導航字和無關長查詢）；增量前 20 頁加一欄「被哪一波改過」。增量大多落在沒改過的頁，就不能歸功給改版。
5. **頁級 DiD**：前 14 對後 14、排除部署日、比日均。窗口被下一波汙染時，另做縮短的乾淨版（案例某波只剩 5 天乾淨），並在報告寫明。
6. **結論只能二選一**：「穩住並擴大了曝光」或「一版比一版高」，並寫明有沒有對照組證據。

案例：4→9 月有效點擊日均約 11 倍（點擊不受 GSC 曝光記錄錯誤影響）。最大的兩段成長是 Google 核心更新（前後 14 日 +178%）和垃圾內容更新（前後 14 日 +32.5%）；在另一組窗（8/3–8/16 對 8/24–9/6）裡，增量的 37% 來自一個從沒改過的 AI 工具頁；第一波改版 DiD（扣掉異常後）−1.1%（p=0.91），安慰劑 +60.7%。結論是：「流量有進步，但沒有證據顯示是改版帶來的。」

例（SaaS）：自然流量三個月翻倍，行銷認為是新版定價頁的功勞。成長引擎表顯示增量的六成來自兩篇從沒改過的教學文，定價頁只占 4%（數字為假設）。結論寫「穩住並擴大曝光；改版本身沒有對照組證據」。

### 步驟 5：因果判斷

**要判定某個站內改動是成因，以下四個條件必須同時成立：**
1. **改動早於斷點。** 以部署完成時間為準，不是 commit 時間。
2. **Google 在斷點前已經重抓受影響的頁。** 看 URL Inspection 的最後檢索時間。注意它只是「最近一次」，不是完整的檢索歷史。
3. **機制夠強。** 改到頁面本體才算。要靠大量重抓才會生效的全站改動，不可能 1–3 小時內見效。
4. **影響範圍與改動範圍一致。** 改的是 A 頁群，掉的卻是 B 頁群，就不成立。

補充規則：
- 只靠時間先後，只能排除「比斷點晚上線的改動」，不能排除較早的改動延遲生效。
- 「斷點前沒有部署」只能排除同時發生的新上線。
- **證據分四類寫**：已觀察事實／合理假說／未獲支持的因果／建議。判定用「成立／部分成立／未證實／錯誤」，各附高、中、低信心。
- **小樣本比率**用 Fisher 精確檢定或兩比例 z 檢定（`rate-test`）。
- **滾動窗安慰劑**：取改動前所有同長度的滾動窗，看觀測值是否落在雜訊範圍內。案例中，改動前 18 個 3 日窗介於 0–23.5%，其中 1 個高於改動後的值，加上 p=0.12，判為雜訊。
- **重現前人數字。** 有人宣稱 10%→26%，你要能找到某個窗口組合重現它；找不到就降為「待驗」。
- **每個干擾上線都做斷點檢查。** 觀察期內每一次其他上線，都用小時資料（`gsc-export --dimensions hour --data-state hourly_all`）比「上線前 24／48 小時」和「上線後 24／48 小時」的曝光加權名次，切段規則照步驟 3 第 15 點。沒有新台階，就記「沒有造成二次下跌」。案例用這個方法排除了新的登入方式和部落格大修。
- **看改動在漏斗的哪一步才生效。** 退步只出現在改動「觸發點之前」的步驟，就不是它造成的。案例：一個只在「輸入問題之後」才出現的提示上線後，回訪跳出率上升約 10 個百分點；但有輸入問題的回訪 session 跳出率三期都是 0%，增加的全是還沒輸入就離開的人，所以不歸因給它。

**懷疑站內改動時：逐版重建，證明每一版到底改了什麼**
- **證據只取已部署的版本。** 本機分支可能落後正式站很多（案例落後 125 個 commit），分析期間工作樹也可能被別的工作階段改動。舊版本一律用版本號從版本庫取出（例：`git show <部署版本>:<路徑>`），不要動工作樹、不要 stash，並把版本號寫進報告。
- **比對「上一個正式部署版本 → 這一個」**，不要只看 merge commit 對第一個父版本的 diff（合併會帶進其他分支的改動）。比對前先正規化換行與空白，否則換行格式會讓小改動看起來像整頁重寫；也先確認路由實際送出的是哪一份檔（同一頁可能有兩份副本）。
- **逐版 SEO diff**：每次部署抽同一組欄位比：title、description、canonical、hreflang、robots、JSON-LD（攤平成「路徑＝值」的葉值再比）、H1–H3（含隱藏和對話框內的）、可見與隱藏字數、連結與錨文字。歷史版本用 Googlebot 手機 UA 在本機渲染（擋掉外部請求，載入後等約 4 秒），並註明它不是 Google 當時看到的畫面。結果寫成「N 個版本中 M 個相同，差在哪裡」，不寫「完全相同」（案例第 1 輪寫「10 個版本渲染完全相同」，第 2 輪逐版比對後是 8 個相同、2 個不同）。`seo-diff` 會自動比原始 HTML 的這些欄位（`--before git:<ref>:<建置目錄>` 取歷史版本）；它不執行 JS，要比渲染後的畫面仍照上面的做法。
- **計數前先講清楚母體**：原始檔、實際對外網址（去重後）、sitemap 是三個不同的數。404 範本、無副檔名和 `.html` 副本都會把數字灌大（案例的連結數 131→52，扣掉 404 範本後是 130→51）。
- **證據留存**：每份原始資料記 SHA-256；兩個子代理交換報告前，先確認雜湊沒變、報告裡的連結都還在、秘密掃描結果為零。

- 例（非占卜站）：
  - 記帳 SaaS 站週二改了定價頁的 FAQ，週四「記帳軟體推薦」掉了 3 名。
  - URL Inspection 顯示定價頁週五才被重抓，而且掉名次的是部落格的比較文。
  - 條件 2 和條件 4 都不成立，不能怪到定價頁頭上。

重大下滑要用兩個獨立的子代理分別調查，再互相挑戰（`prompts/causal-investigation.md`，報告範本 `templates/causal-investigation-report.md`）。

### 步驟 6：GA4 與產品端判讀

- **三種資料各管一件事**：GSC 判自然搜尋成效；GA4／BigQuery 判站內行為；CDN 或伺服器日誌判真實流量和機器人。不拿其中一種去推翻另一種的結論。
- **時區**：GA4 的 `Etc/GMT-10` 其實是 UTC+10（POSIX 的正負號相反）。腳本裡寫死「PT＝UTC−7」的，在夏令時間結束後會錯一天。
- **「自然搜尋 session」有兩種口徑，報告要寫明用哪一個**（BigQuery）：
  - A（主）：看 session 開頭約 5 秒內的來源標記；沒有標記時，看落地頁的 referrer 是不是搜尋引擎。
  - B（對照）：`session_traffic_source_last_click`，也就是 GA4 預設的「最後一次非直接點擊」，接近 GA4 介面。它會把「上次從 Google 來、這次直接打開」的人也算成自然搜尋，數字較大、回訪比例較高，SEO 的轉換因此被高估。
  - 案例同一週：A 1,650、B 1,915。首頁開始率在 B 口徑掉得多（37%→16%），拆開後主要是回訪者；A 口徑的新訪客 62%→48%，只有 21 人，不顯著。
  - 兩個口徑方向一致才下結論；不一致時，先拆新訪客和回訪者。
  - session 一律依「第一個事件」在屬性時區的日期歸日，跨午夜只算一次。
- **跑 BigQuery 前先查完整性**：日表是否齊全、有沒有零事件的小時、沒有 `ga_session_id` 的事件有多少、`user_id` 從哪天開始送。只讀日表，不混 intraday 表。
- **延遲載入**：
  - 機制上，gtag 延後載入時停留很短的訪客可能漏記。要按頁群在斷點前後各算一次「GA4 自然 session ÷ GSC 點擊」或「GA4 page_view ÷ CDN 的 HTML 瀏覽數」，比值有下降才算漏記。
  - 案例：延後載入前後，全站「GA4 ÷ CDN 一般瀏覽器瀏覽」0.317→0.359、「GA4 自然 session ÷ GSC 點擊」1.065→1.078，都沒有下降，結論是沒有可量測的漏算。首頁單頁的 GA4 只記到 GSC 點擊的 42–73%：那是水準比值（點擊不等於 session），以它當分母的轉換率會偏高，但不能算成延後載入造成的量。
- **user_id**：開始送 user_id 後，GA4 介面會把一次造訪拆成兩個 session（膨脹 1.05–1.16 倍）。session 層級的分析改用 BigQuery 的 `user_pseudo_id`＋`ga_session_id`。
- **內建與保留名稱**：自訂參數不要用 GA4 的內建或保留名稱。案例把 `source` 當自訂參數，覆寫了流量來源，報表冒出一個假來源；頁面語系取名 `language`，值被寫進 `device.language`，`event_params` 裡 0 筆（`01` 第 3.1 節）。
- **指標混用**：
  - totalUsers 不是 sessions。
  - 各事件的使用者數不能拿來相除，事件次數也不能拼成順序漏斗。
  - Funnel API 的口徑（依序到達、每步 60 分鐘內）不等於 BigQuery 的「同一 session」，兩者分開用。
  - **最近 2 天整段排除**：後送事件的來源會是 (not set)；案例最近兩個 GA4 日期的事件有 73–100% 被歸到 Unassigned，步驟人數互相矛盾。不是只有最新一天要當暫定。
  - **事件名稱 ≤40 字元**：超過會被截斷，用原名查不到（案例 41 字的失敗事件被截成少一個字）。
  - **同時觸發的兩個事件不能相加**：例如「解鎖完成」與「回站恢復結果」同時送出時，只取一個或去重。
  - **介面改成可以平行操作後，細步驟事件的順序不再可靠**：案例改成「選牌動畫還在展開就能點、第一張牌就送出請求」之後，6 步嚴格順序漏斗從 85% 掉到 61–65%，2 步版本（輸入→看到結果）一直維持 84–89%。掉的是記錄順序，不是使用者；這時只用 2 步版本判讀。
  - **不要把不同身分的資料硬串成一條漏斗**：GA4 的瀏覽器身分、站內帳號、付款紀錄的窗口與身分定義都不同，各自標口徑後再並列。
- **跳出率、SERP CTR 都不是「搜尋滿意度」。**
  - GA4 的跳出率＝沒有構成「互動工作階段」的比例（互動＝停留超過 10 秒、觸發關鍵事件，或看了 2 頁以上）。它不是「回到 Google」的比例，也對不到搜尋字。
  - GSC 的 CTR 是「曝光→點擊」，不是點擊後滿不滿意。平均名次相同，名次分布、SERP 版面、裝置、使用者組成仍可能不同。
  - Google 說它會用彙總、匿名的互動資料評估結果是否相關，但那不是你的 GA4 跳出率或 GSC CTR；不能拿這兩個數字證明「體驗差，所以被降排名」。
  - 案例：前一次結論把「回訪者跳出率 10%→26%」列為護欄字下滑的第二原因。實際只差 3–4 個工作階段（5/47 對 7/28，p=0.12）；而且那個攔截發生在第二頁，看過兩頁的工作階段在 GA4 一定算互動，不可能變成落地頁的跳出。最後刪除。
  - 想驗證「登入牆或免費規則影響體驗」，用產品指標（開始率、完成率、7 日回訪）做訪客分組試驗。它回答產品問題，不回答排名問題（`17` 步驟 6）。
- **網址口徑**：landingPage 沒有尾斜線，GSC 的 page 是完整網址。canonical 指回首頁的重複入口，要和首頁合併計算。
- **機器人與測試流量**：
  - 單一國家的桌機流量占比異常高、參與率只有 1–2%。
  - Lighthouse 測試會打進 GA4 和廣告像素。
  - 預覽網域、平台預設網域、本機的事件混進正式資源：每份報告固定加「主機名稱＝正式網域」條件（`01` 第 3.4 節）。
  - CDN 瀏覽數約有 3/4 是爬蟲或偽裝的機器人。
  - 處理方式：另列一組，不直接刪除；不能推論成「這個國家都是機器人」。
- **落地→產品的比率，先清洗再比。**
  - **高頻瀏覽器**：同一瀏覽器 7 天內輸入或完成 ≥20 次就整個排除，再用 ≥50 次做敏感度檢查。案例首頁有 1–2 個已登入的桌機瀏覽器（像常客或站方自己在測），不排除時開始率 46%，排除後 32%；另一期有 4 個瀏覽器輸入 317 次、抽完 530 次，卻 0 次開始。
  - **內部與測試帳號**：站長、測試信箱、內部高額度帳號。伺服器端資料也要排除，不能只靠 GA4 的內部流量篩選。
  - **集中度**：營收大多來自少數老客戶時，一律並列「含／不含」，不要讓一個人的購買波動決定結論。
  - **付費流量**：廣告開關會改變落地組成。排除付費流量再算一次，結論不變才採用。
  - **爆量週**：爆量帶進來的訪客意圖不同，轉換率也會被灌高（案例爆量週解鎖率 35.5%，平常 27–29%），不能拿來當基準。
  - 兩種清洗口徑的數字並列（案例只影響第一步的分母：21.7% 對 26.9%）。
- **付費類指標**：付費者不到 4–5 人，只寫「樣本不足」，不看趨勢；這種人數下任何差異都不顯著。
- **回訪 cohort**：
  - 窗口：D1＝首次後第 24–48 小時、D7＝第 168–192 小時、D28＝第 672–696 小時，只收觀察滿整個窗的人；第 1–7 日累積另列。
  - **不要拿 Safari 當回訪低的理由，先用帳號重算。** iOS Safari 由腳本寫入的 cookie 最多只留 7 天，理論上 D7、D28 會偏低。用 user_id 把同一個 cohort 重算一次當敏感度檢查。案例的 D7 cohort 有 45% 是 iOS Safari：用瀏覽器算 D7 1.2%、第 1–7 天累積 9.5%，用帳號算 1.1%、9.0%，幾乎一樣；8 天內用過 2 個以上瀏覽器的帳號只有 6%。所以登入會員的跨裝置低估很小，D7 低主要是真的低。未登入訪客的跨裝置情況量不到，報告要寫明。
  - **「首次」要從事件上線日往回查**，不要從觀察窗起點才開始算。案例同一週的 cohort，回查起點不同時，一版是 25 人、D7 8%，另一版是 21 人、D7 0%。
  - **產品規則改了，之後的 cohort 不能和之前比。** 例：贈送額度減少後，登入者每週拿到完整結果的瀏覽器從 66 個降到 22 個，「再次完成」變得更難。報告要把改動日當成 cohort 的斷點。
- **斷點與定義**：
  - 量測斷點前後的數字不可比。付款事件為 0，不等於沒人付款。
  - 次數不等於人數：案例中 63 次失敗只來自 11 個瀏覽器。
  - 步驟定義改了之後，只比端到端。
  - 新功能 0 次觸發，不等於通過驗收。
  - **免費額度、付費牆時機、資格檢查的位置，都是 SEO→產品指標的斷點。** 單獨記 D0、和 SEO 批次錯開；之後的「完整結果」和回訪 cohort 不和改動前比。代價指標與資格檢查的分母怎麼取，見 `17` 步驟 6。

### 步驟 7：本 skill 補上的量測（案例當時沒做，你現在要做）

1. **searchAppearance 切片。**
   - 每次驗收都加 `gsc-compare --by searchAppearance`。只看單一類型時，用 `gsc-export --dimensions date,searchAppearance` 或 `--search-appearance <值>`。
   - 案例沒有切，所以答案膠囊加結構化資料的效果（和其他改動同一窗上線）無法單獨認列。
   - FAQ 搜尋外觀 2026-06 起從 GSC 移除、2026-08 起 API 不再回傳；舊匯出留在 `data/gsc/`，跨這段比較時這一類會「歸零」，不是退步。
2. **用自己的資料建「名次→CTR」曲線。**
   - `gsc-compare` 預設 `--ctr-curve site`：用本站非品牌查詢擬合，每個名次需要 ≥200 次曝光，並保證曲線單調。資料不足的名次，借用公開研究的曲線，再按本站水準縮放。
   - 用途：名次效果的換算，以及判斷「這個名次的 CTR 偏低多少」。
   - 案例只用分段門檻找低 CTR 頁（名次 ≤3 而 CTR <5%、≤10 而 <2.5%、其他 <1%），算不出「這個名次應該有多少點擊」。
3. **同意模式（Consent Mode）。**
   - `instrumentation-audit` 檢查預設值。
   - 在需要同意橫幅的地區，按地區比較「GA4 自然 session ÷ GSC 點擊」，量出同意率造成的漏記。案例沒有處理這件事。
4. **AI 來源與 AI 曝光。**
   - 每週匯出 `ga4-export --preset ai-referrals`，每月判讀（數字小時看月總計，不看週變化）。它要同時涵蓋 GA4 預設的「AI Assistant」管道與舊的 AI 參照網域（`15` 第 10 節）。
   - 案例後來才發現，最大的 AI 來源（90 天 65 次工作階段）在 AI Assistant 管道，不在 Referral；AI 引用追蹤表也五個月沒人填。
   - **AI 的效果分四層量，分開報告**：
     1. 曝光：GSC 生成式 AI 成效報表、Bing AI Performance（人工匯出，用 `ai-reports-import` 匯入）、GEO prompt 追蹤（`11`）。AI 曝光已含在 GSC 一般成效的總數裡，不能相加。
     2. 立即行為：GA4 的 AI 來源工作階段。
     3. 延遲行為：品牌查詢的曝光與點擊、直接造訪、回訪，以及「你從哪裡知道我們」的回答（`01` 第 3.3 節）。
     4. 商業結果。
   - 報告用詞分三級：觀察、關聯、因果。多數 GEO 數字只到前兩級，照實寫。
5. **固定欄位。** 同查詢 CTR、前 10 名天數、對照組淨效果、安慰劑結果，列為每份驗收報告的固定欄位，範本已經內建。

### 步驟 8：寫報告、寫回

- **報告**：用 `templates/review-report.md`，存成 `logs/reviews/<日期>-<波次>-<D+N>.md`。每個數字附資料區間與來源；沒量到的寫「未量測」，不准推估成實數。
- **判定**：寫進 `experiments.json`，四選一：
  - keep：有效，保留並擴大。
  - iterate：無效，記錄原因、不擴大。
  - revert：有害，依 `03` 的回退流程處理。
  - inconclusive：證據不足，延後判讀。
- **基準與舊結論永不覆寫。**
  - 結論錯了，就新增一節「修正 <原節名>」，寫「原說法 → 改成 → 為什麼」，原文保留。
  - 案例中前次結論有 7 處被修正，都是用新節的方式寫。
- **口徑漂移：新規則不得放寬舊門檻。**
  - 改指標定義之前，先用舊腳本、舊篩選把舊數字原樣重現。
  - 新口徑另取名字；舊門檻照舊口徑判。
  - 案例：三方用了三個不同的指標，卻都叫同一條護欄：「4 種寫法合併、全站、10/12–18」是 3.2850；「精確詞、全站、同一窗」是 3.2465；「精確詞＋主頁、10/11–20」是 3.2020。三個數字各自都算對，錯在沒有人寫明口徑。追回舊腳本才確認原口徑是第一個，精確值 3.285。
- 例（非占卜站）：
  - 咖啡站原本的護欄是「『手沖咖啡』全站名次 ≤5」。
  - 有人把它改成「只算指南頁這一個網址」，數字立刻變好看。這等於放寬門檻，不允許。
  - 新口徑可以另外命名並追蹤，但原護欄照原口徑判。

## 決策規則與門檻

| 項目 | 規則／門檻 |
|---|---|
| 資料 | 只用定稿資料（逐日比對 final 與 all 確認）；暫定資料只當預警；部署當地日所涵蓋的 PT 日整天排除 |
| GSC 資料異常 | 比較窗任一端（含去年窗）碰到 2025-05-13～2026-04-27：曝光、CTR、名次不可判讀，只比點擊 |
| 窗口 | 等長、完整日、星期組成相同；不等長時比日均。正式 28 對 28；期中 14 對 14；D+7 看風險與方向、不下結論 |
| 窗長 | 含頭尾的日曆天數，自己算；還沒定稿的日子是「缺」，不補 0 |
| 驗收時點 | D+7 看風險與方向，D+14 看方向，D+28 做決策；標題類改動到 D+28 才判 |
| 同查詢 CTR | Q＝兩期各 ≥50 曝光的查詢（另以 ≥25 做敏感度）。前期＝Σ_Q 點擊₀ ÷ Σ_Q 曝光₀；後期＝Σ_Q(曝光₀,q × CTR₁,q) ÷ Σ_Q 曝光₀,q |
| 扣異常查詢 | 頁面層（或全站）總數 − 異常查詢；匿名查詢保留（`gsc-compare --exclude-query`）；名次標近似值 |
| 平均名次 | 一律曝光加權；零曝光的名次是空值（不是 0，也不是 100）；一定搭配固定集合位移與前 10 名天數 |
| 固定集合 | 前期曝光 ≥10 的（查詢, 網址）；位移＝Σ I₀(P₁−P₀) ÷ Σ I₀；後期消失的組合另列 |
| 頁群比較 | 主結論只用兩個窗都已有曝光的頁；新頁另列 |
| 前 10 名天數 | 平均名次 ≤10.5 且曝光 ≥5 的天數 |
| 雜訊 | Poisson z＝(後−前) ÷ √(前＋後)；\|z\|<2 視為雜訊（`gsc-compare` 的 Signal 欄） |
| 對照組淨效果（DiD） | `gsc-compare`：每日 log((處理＋1)÷(對照＋1)) 的後窗平均 − 前窗平均；淨效果＝e^差值 − 1。p 值用前後標籤的置換檢定（窗口 ≥14 天且為 7 的倍數時以整週置換）。p<0.05 才算顯著。原窗、扣異常、避開異常日各算一次 DiD；報告寫明檢定方法 |
| 手算 DiD（沒有每日資料時） | 處理組在前窗、後窗的點擊為 T₀、T₁，天數為 n₀、n₁；對照組為 C₀、C₁。對照組倍數 r_c＝(C₁/n₁) ÷ (C₀/n₀)。淨效果＝[(T₁/n₁) ÷ (T₀/n₀)] ÷ r_c − 1。p 值用雙尾二項檢定：k＝T₁，n＝T₀+T₁，p₀＝n₁r_c ÷ (n₀+n₁r_c)（條件二項檢定；案例的 −1.1%、p=0.91 就是這樣算的；`rate-test did`） |
| 樣本太小 | 處理組前後合計 <10 次點擊，判「樣本太小」；對照頁的前窗曝光要 ≥50 |
| 安慰劑 | `--placebo-shift <窗長＋排除日數>`（UTC+8 的 28 天窗＝30）。安慰劑與真實結果同方向，且量級 ≥ 真實結果的一半；或同方向且安慰劑 p<0.1 → 判為既有趨勢，不認列 |
| 小時資料 | 只排先後、不量效果；用部署、重抓、外部事件切段；跨部署的小時整桶排除；個位數到二十幾次曝光的段只記錄 |
| 自然搜尋 session | A（session 開頭的來源標記，沒有就看落地 referrer）為主、B（last click）對照；方向一致才下結論 |
| 落地轉換 | 只算自然搜尋 session、同一 session、落地之後；按入口類型分列；先清洗再比（`17`） |
| GA4 比率 | 至少 7 個完整日且入口 ≥30 人，否則寫「待觀察」。Fisher 雙尾 p<0.05 才寫進步或退步。事件占比變成 ≥1.5 倍或 ≤0.67 倍、且 p<0.10，才標「有變化」（`rate-test`） |
| 付費類 | 付費者 <4–5 人只寫「樣本不足」 |
| A/B | 先估要跑幾週（`rate-test power`）。每週 240 人、兩組各 120 人時，分辨 47%→55% 需要 4–5 週。每組只有個位數，不選贏家 |
| 小量 | 不要用 5 次曝光判斷成敗。只多 5 次點擊，寫「達成但量很小」。每 12 小時只有 34–102 次曝光時，±0.5 名都是雜訊 |
| CTR 判讀的最低曝光 | 主題頁在同範圍累積 ≥500 次曝光；小主題 ≥100 次，不足就延長到 56 天 |
| 同窗多改動 | 只能寫「整體方案效果」；另做截斷乾淨版看本波的方向 |
| 口徑 | 新規則不得放寬舊門檻；改口徑前先重現舊數字 |
| 基準與結論 | 永不覆寫；修正一律新增章節 |

**手算公式（腳本不能用、或要驗算腳本時）**

| 用途 | 公式 |
|---|---|
| 點擊變化拆兩塊（中點法） | 曝光效果＝ΔI ×（CTR₀＋CTR₁）÷ 2；CTR 效果＝ΔCTR ×（I₀＋I₁）÷ 2；兩者相加＝ΔC。用在合計列時，頁群組成的變化會落在曝光效果裡 |
| 匿名殘差 | 同條件下 date 維度的總曝光 − query 維度的具名曝光合計 |
| 無效曝光增量占比 | Δ無效曝光（他站導航字＋無關長查詢）÷ Δ全站曝光（案例 8→9 月 34.5%） |
| 排名 DiD | 處理組名次變化 − 對照組名次變化 |
| 預期點擊 | E＝T₀/n₀ × r_c × n₁。限制：r_c 被當成已知常數；點擊不獨立時（爆量、機器人、社群爆紅），p 值會失準 |
| 增益估算 | Δ點擊 ≈ 曝光 ×（目標 CTR − 目前 CTR）；目標 CTR 取本站同名次桶的曝光加權 CTR（排除品牌字、導航字、爆量期） |
| 優先順序 | 損失點擊＝每日曝光 × CTR。案例頭詞每天約 177 次曝光 × 2% ≈ 4 次點擊；護欄字每天 22 次點擊、已經少了 5–8 次 → 先保護護欄字 |
| 首頁拆解 | 每日曝光依序分成：導航爆量字 → 頭詞集合 →「免費」類 → 其他具名查詢；匿名＝總數 − 具名合計 |

口徑提醒：查詢層的覆蓋率逐月在變，會讓查詢層的趨勢偏樂觀；不要用「頁面增量 ÷ 全站增量」當貢獻率（兩者去重方式不同）；全球數字不能標成單一國家。

**判讀矩陣**

| 現象 | 判讀 | 下一步 |
|---|---|---|
| 曝光↑、CTR↑ | 有效 | 保留，複製到相近的頁 |
| 曝光↑、同查詢 CTR 也↓ | 搜尋摘要沒接住 | 改 title、description 和開頭答案（TL;DR，長度照 `09` 第 3.1 步） |
| 曝光↑、全站 CTR↓，但同查詢 CTR 持平或↑ | 被新曝光稀釋，不是變差 | 不動 |
| 名次↑、CTR 持平 | 摘要問題 | 先測標題與摘要，不要加長文章 |
| CTR↑、轉換持平 | 落地頁問題 | 查第一屏入口、CTA 路由、載入速度、漏斗（`17`）；不要加文章 |
| 名次與曝光都不動 | 還沒被重新評估，或意圖不符 | 查索引、canonical、內鏈、意圖、競品；不要大量改寫 |
| 曝光↓ | 能見度問題 | 先查索引、名次、需求（YoY）、外部事件，再決定要不要改內容 |

**逐頁原因分類**（頁級；曝光比＝後期曝光 ÷ 前期曝光；依序判斷，先中先得）

| # | 條件 | 歸類 | 下一步 |
|---|---|---|---|
| 1 | 前期曝光 ≥50 且曝光比 <0.4 | 曝光消失 | 查索引、canonical、整頁掉出（看逐週曝光） |
| 2 | 名次差 ≥1 名 | 名次下滑 | 查 SERP、競品、重抓時間 |
| 3 | 名次進步 ≥1 名，但曝光比 <0.8 | 查詢組合改變 | 拆到查詢層級，看是不是丟掉離題字 |
| 4 | 曝光比 <0.75 | 曝光下降、名次持平 | 查需求（`--yoy`、Trends） |
| 5 | CTR 比 <0.75 | CTR 下降 | 查 SERP 版面與摘要 |
| 6 | 其餘 | 小幅波動 | 不動 |

- **同時做「去索引檢查」**：列出前期曝光 ≥100、後期曝光＝0 的頁。案例一頁都沒有，所以直接排除「整頁被除名」。
- 案例 7→8 月少了 982 次點擊：「曝光下降、名次持平」161 頁合計 −502；「名次下滑」406 頁 −323；「曝光消失」66 頁 −205；「CTR 下降」59 頁 −117。主因是能見度，所以那次不該去改標題。
- **退步頁分流**：沒有新改動 → 先人工看 SERP，再做單一摘要的小實驗；已有新改動 → 等 `lastCrawlTime` 晚於 D0 再判；樣本小 → 先診斷，不排最高優先；原本在成長的頁 → 保護核心 title，看核心詞的同查詢 CTR，不因整頁平均 CTR 微降就判失敗。
- **留意名單**（文章等大量頁）：前窗日均曝光 ≥3 才列入；名次差 ≥3 名或曝光減半，標「留意」；D+14 再看一次，D+28 才下判斷。
- 例（電商）：某商品頁前期曝光 400、曝光比 0.35 → 歸「曝光消失」，先查是不是下架後被改成 noindex，不要先改標題。

**結論用詞**：有效／無效／有害／證據不足。期中另可用：達成、窗內達成但未維持、短暫達成、未達成、無法判斷（被後續改動汙染）、需再測、意圖位移、承接轉移、技術完成但效果無法量測、整體方案效果、樣本不足、待觀察（偏退步）。

## 常見錯誤（案例站實際發生過）

1. **只做前後比。** 第一波 +46～58%；加對照組（扣掉異常後）是 −1.1%，安慰劑 +60.7%。
2. **把一頁的勝利當成整波有效。** 第二波的 4 頁摘要：整波清洗後 +7.7%（p=0.65），不顯著；截到下一波之前的乾淨 5 天是 −0.9%；早期的點擊增量多半來自他站導航字。
3. **全站 CTR 一跌就判變差。** 同查詢 CTR 其實在升（1.80%→2.12%）。
4. **被平均名次騙。**
   - 低名次的查詢消失後，平均反而「變好」（8.53→6.80）。
   - 新曝光集中在第 10 名附近時，平均會「變差」（6.78→9.25）。
   - 整頁掉出結果時，平均名次看不出任何變化。
5. **以為名次能換算成頁碼。**
   - 曝光只在結果出現在使用者正在看的那一頁時才計入。
   - 第 11 名可能是知識面板，也可能是第 2 頁第一筆。
   - 「零曝光」推不出「在第 2–3 頁」。
6. **用查詢層判斷漲跌。** 帶 query 維度就會丟掉匿名查詢；案例中某月 55% 的曝光沒有查詢字。overview、page 加總、query 加總三者互不相等。
7. **只抓 API 的第一頁。** rowLimit 預設 1,000、上限 25,000，要用 startRow 一直翻頁，翻到回傳不滿一頁為止（`gsc-export` 已處理）。
8. **把時間吻合當成因果。**
   - 「Google 10/22 才重抓，所以能排除其他改動」，這個推論是錯的。
   - 最後檢索只是「最近一次」；被排除的改動也根本不在那一頁。
9. **小樣本下結論。** 某個轉換改動被列為「第二原因」，差距只有 3–4 個 session（p=0.12）。滾動窗安慰劑顯示落在雜訊內，宣稱的比率也無法重現，最後刪除。
10. **沒查歷史就下結論。** 「大字掉回改定位前的 15–19 名」是錯的：改定位前，那三個字本來就是 0 曝光。
11. **口徑漂移。** 三方用了三個不同的指標（3.2850／3.2465／3.2020），卻都叫同一條護欄，沒有人發現。
12. **用混合日判讀。** 原訂用「含部署日的那一週」判護欄，後來改用下一個完整的 PT 週。
13. **定義改了還照比。** 「按解鎖→成功 47%→81%」看起來達標，其實是改版改了定義。
14. **把舊匯出當成新資料。** 檔頭寫的日期不代表資料完整。
15. **讓檢查永遠紅燈。** 驗證腳本的期望值過時，每次固定紅 6 項，真正的新失敗就被淹沒了。
16. **用到受汙染的基準。** 交接文件裡的「每週 session 數」，混進了 4 天爆量。
17. **把無效曝光當成成長。** 8→9 月的曝光增量裡有 34.5% 是無效曝光：他站導航字和無關長查詢。（同時期常被引用的「曝光 +45%」是滾動 28 日窗，和 34.5% 的分母不同，不能寫成「+45% 裡有 34.5%」。）
18. **用全來源平均判轉換改動。** CTA 深連結那一波，全來源的內容頁輸入率 10.2%→8.6%，看起來失敗；只看自然搜尋 session 其實是 25.0%→26.7%（步驟 3 第 14 點）。
19. **扣異常查詢時連匿名查詢一起扣掉。** 用「查詢×頁面」排除後再加總，匿名查詢整個消失，和其他版本不能比（步驟 3 第 4 點）。
20. **靠單一小時下定論。** 「下滑早於部署」只靠一個 8 次曝光的小時，第 2 輪被推翻（步驟 3 第 15 點）。
21. **混用兩個事件的證據。** 「他語言版在進步」是護欄字下滑期間的觀察，被寫進大字重排那天的判斷（步驟 4）。

常用組合：

```bash
# 正式驗收（D+28）：對照組、安慰劑、季節性、搜尋外觀切片、核心字的前 10 名天數
node scripts/gsc-compare.mjs --wave W-2026-10-07-home --checkpoint D+28 \
  --placebo-shift 30 --yoy --by searchAppearance --target-query "<核心字>"

# 用網址規則指定處理組與對照組（例：只改了 /reviews/ 底下的頁，對照組是 /guides/）
node scripts/gsc-compare.mjs --deploy-date 2026-10-07 --window 28 \
  --treatment "^/reviews/" --control "^/guides/" --placebo-shift 30

# 「避開異常日」版本：手選兩段乾淨的 7 天
node scripts/gsc-compare.mjs --pre 2026-09-27:2026-10-03 --post 2026-10-15:2026-10-21 --label clean-week

# 「扣異常查詢」版本：先列出候選查詢、逐條確認，再用總數減去它們（匿名查詢量保留；名次是近似值）
node scripts/gsc-export.mjs --dimensions query --days 56 --query-regex "(?i)(otherbrand|他站名)" --name spike-candidates
node scripts/gsc-compare.mjs --deploy-date 2026-10-07 --window 28 \
  --exclude-query "(?i)(otherbrand|他站名)" --label excl-spike

# 找台階：小時資料只保留約 10 天，切段規則見步驟 3 第 15 點
node scripts/gsc-export.mjs --dimensions hour --data-state hourly_all --start 2026-10-17 --query "<核心字>"

# 邊界曝光占比：取逐日資料自己算
node scripts/gsc-export.mjs --dimensions date,query --days 28 --query-regex "^(<字1>|<字2>)$"

# 產品端比率（例：自然落地的開始率，前後各 14 個完整日）
node scripts/rate-test.mjs --before 18/310 --after 31/298 --days-before 14 --days-after 14
```

## 範本

- `templates/review-report.md`：期中與正式驗收報告。固定章節包括資料與口徑、多版本、同查詢 CTR、對照組與安慰劑（含逐網址預期表）、護欄、索引、產品端（依入口類型）、原因表、待決事項。
- `templates/acceptance-checklist.md`：D0、D+1、D+3、D+7、D+14、D+28 各自要檢查什麼。

- `templates/wave-record.md`：上線前的預先登記（類型、預期方向、相關查詢、護欄、對照組）。驗收時拿它對答案。
- `references/17-sxo-search-landing-conversion.md`：搜尋落地轉換的做法、門檻與 BigQuery 查詢範本。
