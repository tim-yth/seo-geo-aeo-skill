# 01 · 網站量測埋點：在哪裡插什麼、怎麼跟使用者溝通

> 資源備齊（`00-resources-onboarding.md`）只代表「拿得到資料」。網站本身沒埋好量測，GA4 裡的數字就是錯的，之後每一次驗收都會被誤導。
> 這一步要在第一波 SEO 改動之前完成，並且有自己的「量測 D0」。
> 案例站（繁中塔羅占卜工具站）照原計畫送了一個叫 `language` 的參數，到正式驗收才發現 BigQuery 裡一筆都沒有；伺服器送的購買事件約 19 天一筆都沒進 GA4。兩件事都是「程式上線了、測試也過了」，卻沒有人逐筆查收件。

## 1. 三種證據，不可混用

| 證據 | 代表什麼 | 不代表什麼 |
|---|---|---|
| 正式站資產裡有事件程式碼 | 程式已上線 | GA4 收得到 |
| 測試環境 dataLayer／DebugView 看到事件 | 觸發邏輯正確 | 正式站流量都有送 |
| GA4 報表／BigQuery 隔日看到事件與參數 | 收件完成 | 收件率 100%（擋廣告、同意模式、延遲載入都會漏） |

報告裡要明寫是哪一種證據。沒有 GA4 收件證據，不能把「量測完成」打勾。

## 2. 先稽核現況（skill 自動做）

```bash
node scripts/instrumentation-audit.mjs            # 線上抽樣＋原始碼掃描
```

它會檢查並列出：
- 每個頁面分組（首頁／工具頁／文章／分類…）是否都載入 GA4（`G-` 評估 ID）或 GTM；有沒有重複安裝、多個 GA4 ID。
- gtag 是否被延遲載入（例如互動後或幾秒後才載）→ 可能少算短停留訪客。
- 同意模式（Consent Mode）是否設定預設值。
- GSC（`google-site-verification`）、Bing（`msvalidate.01`）驗證、IndexNow 金鑰檔是否在線。
- 原始碼的框架與可插入位置，以及現有 `gtag()`／`dataLayer.push` 呼叫（檔案:行號、事件名、參數）。
- 參數撞到 GA4 內建或保留名稱（`language`、`source`、`medium`、`campaign`、`page_location`…）或看起來像個資（email、uid、提問內容、姓名、電話）。

輸出：`logs/reviews/<日期>-instrumentation-plan.md`（給使用者看的插入計畫）＋ `data/instrumentation/<日期>-audit.json`（給 agent 的原始結果）。

## 3. 設計量測計畫（SEO 需要的最小集合）

### 3.1 每頁都要有
- GA4 基本 `page_view`（含正確 `page_location`）。
- 頁面分類維度：每頁送一次 `seo_landing_view`（或在 `page_view` 加參數），帶：
  - `surface`：`home`／`seo_tool`／`blog_article`／`blog_category`／`product`… 依網站的頁面分組。
  - `page_type`：更細的模板類型（例如 `card_meaning`、`guide`、`landing`）。
  - `page_language`：頁面語系（例：`zh-TW`、`en`）。**不要取名 `language`**：gtag 有同名的內建欄位（使用者的瀏覽器語言），GA4 會把值寫進該事件的 `device.language`，BigQuery 的 `event_params` 裡一筆都找不到，同一個維度還會混進「網站語系」和「瀏覽器語言」兩種意思。也可以叫 `content_language`，全站擇一。
  這讓「自然搜尋落地 → 開始使用 → 完成 → 註冊／付費」可以依頁型拆開，不必靠 URL 正則猜。
- **語系值只在一個共用函式裡對應**（例：`zh-Hant`、`zh-Hant-TW` → `zh-TW`），每個送事件的模組都呼叫它，不要各自判斷。案例修好對應後，主流程事件的 unknown 從 93% 降到 2% 以下；另一個模組沒用這個函式、不認 `zh-Hant`，它送的 3 個事件仍約 90% 是 unknown。上線後逐事件看 unknown 占比，不要只抽一個事件。
- 參數改名隔天（第一個完整日）起算新口徑；改名當天記「量測 D0」、不納入比較；改名前的舊資料改從 `device.language` 讀，並在報告註明。
- 搜尋落地轉換（`17`）還需要：開始事件帶 `placement`（入口位置的列舉值，例：開場提問框／入口頁 hero／手機底部列／文末 CTA），用來比較哪個入口有用；不帶提問文字。

### 3.2 網站的核心動作漏斗（依網站換名字）
以「工具型網站」為例（案例站是線上占卜工具）：

```
input_completed → tool_start → tool_completed → signup / login → checkout_start → purchase
```

每個事件寫成「事件字典」，**一定要有「不代表什麼」欄**，避免日後誤讀：

| 事件 | 語意 | 不代表什麼 | 參數白名單 |
|---|---|---|---|
| `tool_start` | 一次主要請求開始送出 | 使用者看到首頁、點了按鈕 | `surface`、`page_type`、`page_language`、`placement` |
| `tool_completed` | 成功結果開始呈現在畫面 | 使用者讀完、覺得有用 | `surface`、`page_type`、`page_language` |
| `tool_failed` | 該請求失敗（帶固定 `failure_code`） | 使用者離站的所有原因 | 同上＋`failure_code` |
| `checkout_start` | 使用者開始結帳；同時把瀏覽器的 GA4 client_id、session_id 存進訂單 | 會付款 | `purchase_type` |
| `purchase` | 伺服器確認收款 | 前端按下付款鈕 | `value`、`currency`、`transaction_id`、`purchase_type` |

規則：
- **參數白名單**：只送固定列舉值。絕不送使用者輸入文字、email、UID、姓名、答案內容、requestId、原始錯誤訊息、完整 URL query。
- **網址本身也會被送出**：GA4 的 `page_view` 會自動帶完整網址（`page_location`）和來源網址。
  - 金流、登入、魔術連結回站時，網址上的 session、token、email 一類參數，要在任何分析或廣告腳本載入前用 `history.replaceState` 清掉，並寫成部署前測試（案例的測試就叫「首頁在分析腳本執行前移除回跳祕密參數」）。
  - 站內不要用網址 query 傳使用者輸入。內容頁把提問交給工具頁時，用同一分頁的 `sessionStorage`、讀一次就刪；提問會跟著網址進 `page_location`、伺服器與 CDN 日誌、Referer（做法與瀏覽器測試見 `06` 第 3b 步，為什麼要做見 `17`）。
- **不用 GA4 內建或保留的名稱當自訂參數**：
  - 案例：分享事件帶了自訂 `source` 參數，覆寫了流量來源，報表冒出一個假的「推薦來源」。
  - 案例：頁面語系照原計畫取名 `language`，BigQuery 的 `event_params` 裡 0 筆（3.1）。
  - 上線隔天逐一查每個自訂參數的非空比例（第 6 節）。
- **失敗與成功不互斥**：同一人先失敗再重試成功，兩者都會出現；不能相加當 100%，失敗用「暴露率」呈現。
- **跳到站外再回來的流程**（第三方登入、付款）要有 `started`／`completed`／`failed` 三個事件，外加「返回失敗」。少了最後一個，中途消失的人就無法定位：案例新增一種第三方登入後，11 人開始、7 人完成，另外 4 人既沒完成、也沒有失敗事件，查不出是卡在授權頁還是返回時出錯。
- **付款事件從後端送**（GA4 Measurement Protocol），金額以伺服器確認為準；前端送會漏掉付完沒回站的人與續訂。後端送要做對四件事：
  1. **接回原工作階段**：`checkout_start` 時把瀏覽器的 client_id 與 session_id 存進訂單，伺服器送 `purchase` 時帶上。用帳號雜湊或隨機值當 client_id，來源一律變成 Unassigned（案例收到的 8 筆裡有 7 筆如此）。
  2. **「送出成功」不等於「GA4 收到」**：除錯端點只檢查格式，不檢查 api_secret 與 measurement_id；正式端點用錯密鑰也會回 2xx，事件直接被丟掉。密鑰要用 Admin API 對到「同一個網站資料串流」：在記憶體裡和正式環境的設定比對，只輸出「一致／不一致」，不印密鑰。送出失敗要留紀錄並重試，不要只寫一行警告。
  3. **在正式執行環境跑一次送出程式**：無伺服器平台的 API 和 Node 不完全一樣。案例的 mock 測試全過，正式環境卻在送出前就丟錯：先是密鑰對錯資料串流，修正後又碰上正式環境不支援一個 fetch 選項，前後約 19 天，伺服器的購買事件一筆都沒進 GA4，中間一次「修正」和一次換密鑰都沒解決。部署前用平台的本機模擬器實際執行一次（攔下對外請求即可）。
  4. **補送與重試**：漏送的事件只能在約 72 小時內補送（帶原本的時間戳）；更早的會被記到錯的日期，不要補，那段期間的營收以金流後台為準並在報告註明。逾時或網路錯誤時 Google 可能已經收到，只重送 `purchase`（以 `transaction_id` 去重），不要重送自訂的完成事件，以免漏斗重複計數。
  - 不要為了測試製造真實付款，也不要往正式端點送假交易。唯一的驗收方式：等下一筆真實交易，隔天用 `transaction_id` 查到它（第 6 節）。
- **上線前的 0 不是 0 人使用**：事件從部署那天才開始收，不能拿上線前的空值算提升比例。

### 3.3 來源歸因
- AI 來源：GA4 預設管道「AI Assistant」加上自訂管道群組「AI 推薦」（只補預設管道沒涵蓋的來源，例如 Perplexity）；兩者怎麼分工見 3.4 第 10 點。GEO 成效靠它看，但它只是下限。
- 站內分享連結帶 UTM（`utm_source=share_xxx&utm_campaign=...`），不要用事件參數假裝來源。
- A/B 實驗加 `experiment_id`、`experiment_variant`。
- **「你從哪裡知道我們？」**：在註冊或第一次使用後問一題，選項含搜尋引擎、AI 助理、社群、朋友介紹…；選了 AI 助理的，再請對方寫「你問了 AI 什麼」。答案存在自己的後端（自由填寫的文字屬於使用者輸入，不送 GA4；GA4 最多只送選項代碼）。AI 介紹之後的造訪多半不帶參照：第三方觀測約只有 42% 發生在 24 小時內、超過 97% 不帶 AI 參照參數（只當假設），所以只看 GA4 的 AI 參照流量會低估 GEO（四層量測見 `02` 步驟 7）。

### 3.4 GA4 後台要使用者自己按的設定（skill 列清單、使用者執行）
1. 自訂維度：把每個事件參數（`surface`、`page_type`、`page_language`、`placement`、`failure_code`、`purchase_type`…）註冊成「事件範圍自訂維度」。**沒註冊的參數報表看不到，也不會回補。**
2. 關鍵事件：把真正的轉換（註冊、完成主要動作、購買）標為關鍵事件。
3. 資料保留：改成 14 個月。
4. 連結 Search Console（GA4 → 產品連結）。
5. 開 BigQuery 每日匯出（不回補歷史，越早開越好；見 `00` 第 1.1 節）。
6. 內部流量篩選（排除自己與團隊 IP）。
7. 記下資源時區（之後所有 GA4 比對都要標註）。
8. **不想要的參照連結**（管理 → 資料串流 → 設定代碼 → 列出不想要的參照連結）：加入登入服務的網域（身分驗證網域、OAuth 回呼頁）和金流結帳網域。不設的話，登入或付款後回站會變成一次新的「參照」工作階段，原本的自然搜尋來源就斷了，SEO 帶來的轉換被低估。案例首頁 28 天有 20 個工作階段來自登入網域、11 個來自金流網域。
9. **在地搜尋引擎有沒有被記成參照**：查「工作階段來源」裡的 Yahoo（台灣、香港）、Naver 等搜尋網域；被歸到「參照」的，用自訂管道群組歸回「自然搜尋」。案例首頁有 40 個 Yahoo 台灣／香港的工作階段被記成參照。
10. **AI 來源先看預設管道**：GA4 已有預設管道「AI Assistant」（2026-05-13 起，不回溯；細節見 `15` 第 10 節）。案例 90 天 65 次來自 AI 對話服務的工作階段都在那裡，不在 Referral；只看 Referral 會漏掉最大的 AI 來源。但 Google 沒有公開完整清單，Perplexity 這類來源可能仍算 Referral，所以照樣補一條自訂規則（「AI 推薦」群組），只收預設管道沒涵蓋的來源，兩邊不要重複計算。
11. **只收正式網域**：預覽網址、平台預設網域（`*.pages.dev` 這類）、本機（localhost）不要載入正式的 GA4 評估 ID；做不到時，在 GA4 建資料篩選器，或在每份報告固定加「主機名稱＝正式網域」條件。案例的 GA4 全歷史混有本機和多個預覽網域的事件，轉換分析只能事後限定正式網域重算。

## 4. 插入位置對照（依框架）

| 框架 | 全站標籤放哪 | 事件放哪 |
|---|---|---|
| 純 HTML／靜態產生器（Hugo、Jekyll、Eleventy、Astro） | 共用 layout 的 `<head>`（`baseof.html`、`_layouts/default.html`、`Layout.astro`） | 共用 JS 檔，依 `data-surface` 屬性送 `seo_landing_view` |
| Next.js | App Router：`app/layout.tsx` 用 `next/script`；Pages Router：`pages/_app.tsx` 或 `_document.tsx` | client component 的事件處理器；付款在 API route 用 Measurement Protocol |
| WordPress | Site Kit 或 GTM 外掛；或子主題 `functions.php` 的 `wp_head` | GTM 觸發條件，或主題 JS；WooCommerce 用其購買 hook 走伺服器端 |
| Shopify | 線上商店 → 客戶事件（Customer events）／Google & YouTube 應用 | 主題 `theme.liquid`；購買用官方整合，不要重複送 |
| Webflow／Wix／Squarespace | 網站設定的自訂程式碼（head） | 平台事件或 GTM |
| Cloudflare Worker／邊緣改寫 | `HTMLRewriter` 注入 `<head>`（注意快取版本號） | 前端 JS；後端事件在 Worker 用 Measurement Protocol（部署前在平台的本機模擬器實跑一次） |
| 用 GTM 的任何網站 | GTM 容器（只裝一次） | GTM 變數＋觸發條件，`dataLayer.push` 由網站送 |

注意：
- 只裝一套（gtag 或 GTM 擇一），避免重複計算。
- 不要為了 PageSpeed 把 gtag 延到「互動後或 N 秒後」才載入，除非接受可能少算。已經這樣做時，按頁群在改動前後各算一次「GA4 page_view ÷ CDN／伺服器 HTML 頁面瀏覽數」或「GA4 自然 session ÷ GSC 點擊」，有下降才在報告裡加註漏記比例。案例延後載入前後，全站這兩個比值都沒有下降（0.317→0.359、1.065→1.078），沒有量到可測的漏算；首頁單頁的 GA4 只記到 GSC 點擊的 42–73%，那是水準比值（點擊不等於 session），不能當成延後載入造成的量。
- 改 JS 檔後更新快取版本號（`?v=日期`），並確認正式站載入的是新版本。

## 5. 跟使用者溝通的方式

量測改動會碰到正式網站、可能碰到隱私與同意橫幅，所以：

1. **先給計畫，不先動手**。用下面的格式交給使用者，白話說明，每列都要能回答「為什麼需要」：

```markdown
## 量測插入計畫（請確認）

| # | 位置 | 要加什麼 | 量什麼／為什麼 | 需要你做什麼 |
|---|---|---|---|---|
| 1 | 全站 <head>（app/layout.tsx） | GA4 標籤 G-XXXX | 所有頁面瀏覽，現在文章頁沒有裝 | 確認要用的 GA4 資源 |
| 2 | 文章頁模板 | seo_landing_view（surface=blog_article） | 搜尋進來的人有沒有往下用工具 | 無 |
| 3 | 付款完成的後端 | purchase（伺服器送出，帶回原本的工作階段） | 真正收款，含沒回到網站的人 | 提供 Measurement Protocol API secret（存進 secrets/） |
| 4 | GA4 後台 | 註冊 surface／page_type 自訂維度、不想要的參照連結 | 不註冊報表看不到；登入或付款回站會切斷來源 | 你在 GA4 後台照步驟按（約 10 分鐘） |
```

2. **分清楚誰做什麼**：程式碼改動由 skill 做（使用者核准後）；GA4／GTM 後台設定、同意橫幅的法律判斷、API secret 由使用者準備。缺什麼就照 `00-resources-onboarding.md` 的步驟帶使用者補，拿到後記進 `.seo-agent/`。
3. **不要用技術名詞嚇人**：說「搜尋進來的人有沒有開始使用」，不說「landing-to-activation funnel」。
4. **上線後回報三種證據的進度**（第 1 節），未收件就說未收件。

## 6. 上線後驗證順序與資料成熟時間

1. **上線當日**：記錄「量測 D0」（部署完成時間、commit、資產版本）到 `logs/changes.md`，與 SEO 波次 D0 分開；檢查正式資產有事件、DebugView 看得到。
2. **隔天**：
   - GA4 報表／BigQuery 有事件與參數值；缺件先查流量是否真的經過該流程、瀏覽器阻擋、腳本版本、匯出延遲，不直接判定沒人用。
   - **逐一查每個自訂參數的非空比例與 unknown 占比**。任何一個是 0，先懷疑撞到內建名稱：`language`、`source`、`medium`、`campaign`、`term`、`content`、`page_location`、`page_referrer`、`page_title`…；改名後重記「量測 D0」。
3. **成熟時間**：第一個完整日＝D0 隔天（D0 當天不滿 24 小時，排除）；第一個完整 7 日窗約 D+8 可看；28 日窗約 D+29 可看。
4. **漏斗**：用 GA4 Funnel（依序到達）或 BigQuery 以 `user_pseudo_id + ga_session_id` 聚合；不能拿各事件總數相除拼成漏斗。
5. **回訪 cohort**：D7 定義成「首次事件後第 168–192 小時有再次完成主要動作」，只納入已觀察滿 192 小時的人；第 1–7 日累積回訪另列，不混稱 D7。「首次」要從事件上線日往回查；用帳號重算當敏感度（見 `02` 步驟 6）。
6. **購買事件逐筆對帳**（上線後第一週每天，之後每週）：
   - 從伺服器或金流紀錄取每一筆成功付款，用同一規則算 `transaction_id`，到 BigQuery 日表和 Data API 各查一次：每筆都要有、只有 1 筆、帶 `ga_session_id`、同一使用者付款前有 `checkout_start`。
   - **購買吻合率**＝GA4 找得到（BigQuery 與 Data API 都有）的伺服器付款筆數 ÷ 伺服器付款筆數；另查重複（同一 `transaction_id` 出現 >1 次）和孤兒（GA4 有、伺服器沒有）。
   - 當天的付款等隔天日表再查；報表幣別和交易幣別不同時，GA4 顯示的是換算後的金額。
   - 案例修好之後逐筆對帳：8 筆裡 7 筆已在 GA4、沒有重複、都接得回瀏覽器工作階段。對帳結果寫進事件字典的「上線 D0」欄。
   - 無伺服器平台的即時日誌通常不保存，漏報只能靠這種逐筆對帳發現；平時的持續監測見 `13` 的「關鍵事件斷流檢查」。

## 7. 案例中踩過的量測坑（每份報告都要檢查）

- **GA4 資源時區不是當地時區**（案例是 UTC+10，不是台北）。GSC 日期是美國太平洋時間。跨來源比對前先對齊並註明。
- **gtag 延遲載入**（為了速度改成互動後才載）：機制上會少記短停留訪客，sessions 變少、參與率變高、以 landing 事件為分母的轉換率虛高。要按頁群在改動前後量，不要只憑機制下結論（第 4 節的案例：全站前後比沒量到下降）。
- **機器人 Direct 流量**：某國桌機大量 Direct、參與率約 2%，拉低全站平均；分析時分開看。
- **自訂參數撞到內建名稱**：`source` 參數 → 出現假推薦流量；`language` 參數 → BigQuery 裡 0 筆。
- **伺服器購買事件約 19 天沒進 GA4**：密鑰對錯資料串流，修正後又因正式執行環境不支援一個 fetch 選項而在送出前丟錯；mock 測試全過。超過 72 小時的事件只能放棄，營收靠金流紀錄補（早期報告只看到其中 5 天）。
- **購買事件從前端改後端那天**，前後付費數字口徑不同，比較從改後完整日起算。
- **新自訂維度不回補**；失敗分類細分後，歷史資料無法重分類，只能從上線隔天起比。
- **某些模板沒送 landing 事件**：抽查時發現牌義頁有 GA 腳本但缺頁型事件，自然落地 175 個 session 只有 16 個（約 9%）帶事件 → 先修量測，再談 CTA 優化，也不能拿它判 CTA 無效（`17`）。
- **預覽站和本機的事件混進正式資源**（3.4 第 11 點）。
- **跳到站外的流程沒有「返回失敗」事件**：4 個人憑空消失（3.2）。
- **不同 Google 帳號權限不同**：BigQuery 用 A 帳號被拒、B 帳號可讀，不要誤判成匯出壞掉。
