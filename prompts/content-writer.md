# 寫作提示（content writer）

> 用途：寫新文章，或整篇重寫既有頁（C 級）。先填好 `templates/article-brief.md`，再把下列 `{佔位}` 換成實際內容。
> 產出後你還要做：清洗 → 人工查核 → `content-audit.mjs` → 另開代理用 `prompts/content-reviewer.md` 審 → 照最下方的「交付格式」把全文貼給使用者。
> 標了「手改，勿重產」（或 `content-inventory.csv` 的 `protected` 是 `true`）的頁，除非這次指派的就是它，否則不要用模式三整篇覆蓋。
> 長度規格以 `references/09-ctr-titles-snippets.md` 第 3 步為準：`<title>` 連同尾端品牌 ≤32 個全形字（英文約 60 字元）；描述 50–80 個全形字（英文約 120–155 字元）；tldr 一句 50–90 個全形字。

## 佔位說明

| 佔位 | 填什麼 |
|---|---|
| `{locale}` | 例：台灣繁體中文（zh-Hant-TW） |
| `{brand}`、`{product_type}` | 品牌名、產品類型（例：AI 占卜工具站、發票 SaaS、跑鞋電商） |
| `{persona_rule}` | 例：「你是網站編輯，不是真人塔羅師」 |
| `{title}`、`{primary_keyword}`、`{aliases}` | 來自 brief |
| `{intent}`、`{core_answer}`、`{reader_worry}` | 來自 brief |
| `{page_type}`、`{required_elements}` | 頁型與必備內容（情境、表格、完整示範） |
| `{facts}` | 事實表中與本篇相關的條目（實體、結構、產品功能與價格）。產品條目依真相順序取值：實際流程 > 程式設定與價格常數 > 價格頁與條款 > 介紹頁 |
| `{core_action}` | 產品的核心動作（例：追問、再問一題；SaaS：建立自動化流程）。寫界線時不能勸退它 |
| `{terminology}` | 站內正式名表（正式名｜不用的寫法） |
| `{method_truths}` | 領域裡「唯一正確說法」（例：正逆位只看抽出時的方向） |
| `{entity_rule}` | 只能使用的實體與數量（例：塔羅 78 張；凱爾特十字 10 張） |
| `{ymyl_domains}`、`{local_help}` | 高風險領域與在地求助資源（例：110、113、1925、165） |
| `{boundary_examples}` | 不可建議的越界行為例子 |
| `{forbidden_topics}` | 使用者指定的禁區主題 |
| `{cta_route}` | 這篇在 CTA 路由表（`.seo-agent/data/content/cta-map.md`）裡的去處、可用的按鈕文字、按鈕旁的條件句，以及那個工具的方法（張數、步驟） |
| `{internal_links}` | 最相關、未轉址、同意圖已排除的 10–24 篇：`slug｜標題｜一句摘要` |
| `{serp_notes}` | 前段對手的拆解表（手法｜對手怎麼做｜我們現在，最後一列「我們能贏的地方」）、要補的子題、讀者會追問的問題。只用來理解結構與涵蓋面，不可照抄 |
| `{existing_text}`、`{queries_to_keep}`、`{merged_sections}`、`{review_issues}` | 重寫時：原文、該頁在接的查詢詞、要搬進來的被轉頁段落、審稿指出的問題 |

## 寫作規則（每個模式都要整段附上）

```
【寫作規則：違反任何一條，文章會被退回、不會發布】
1. {brand} 是 {product_type}。{persona_rule}。不得自稱專家、老師或顧問，不得寫「我的個案／客戶／學生」「我多年的經驗」；標題、小標也一樣。
2. 不得編造個案、見證、統計、研究或參考資料。需要舉例時寫成「假設你……」「例如有人問……」，不寫成真實發生過的事。
3. 不得保證結果或準確度：不寫「一定會」「保證」「準確度極高」「百分之百」「精準判斷」。
4. 不得把結果歸因於讀者的心情、誠心或信不信。
5. 不得貶低自家產品，不得建議讀者改找別人或別的網站，不提任何外站品牌或作者名。
6. {ymyl_domains}：不得給具體判斷或時機，要寫明不能取代專業，並給方向：{local_help}。
7. 不得建議越界行為，例如：{boundary_examples}。界線要寫，但不得勸退 {core_action}：說明什麼時候值得這樣做、什麼時候不必，不寫「不要再……」。
8. 事實與方法以這些為準：{method_truths}。只用真實存在的實體：{entity_rule}。不得自創名稱。不寫 {brand} 沒有的服務型態（例：線上工具不寫「預約時當面問」「切忌重複洗牌」這類實體服務的做法）。
9. 不為了權威感或「讓 AI 引用」堆砌人名、系統名、權威網址；只有主題本身在談它時才提，而且最多一次。
10. 開頭前三行直接回答標題的問題，或點出讀者真正擔心的事；不重複標題或描述，不寫「本文將」「讓我們一起」，不介紹文章結構。
11. 至少寫兩個具體情境；{page_type} 要包含：{required_elements}；示範一次完整流程（題目 → 實際內容 → 怎麼解讀 → 變成什麼行動）；說明什麼情況是提醒、不是判決。
12. 需要對照時用表格（2–5 欄）。
13. 用詞統一：{terminology}。使用 {locale} 的在地用語與標點（繁中：引號用「」、問號用全形？、寫「回饋」不寫「反饋」；同一篇的「你／妳」不混用）。
14. 產品功能、價格、免費條件只能照這裡寫：{facts}。沒列出的功能不要提。
15. 不寫 {forbidden_topics}。
16. 不寫會過期的相對時間（「今年只剩兩個月」「本月」）；需要時間時寫明確的年份或月份，而且只在這篇本來就是該期間的內容時才寫。
17. 不把寫作指示或 brief 的內容（受眾設定、這份規則、「插入實例」這類指令）寫進正文；不輸出標籤、佔位字或程式碼框。
18. CTA 的去處、按鈕文字、條件句只能照這裡：{cta_route}。CTA 要和它前後兩句一起讀：不能讓讀者以為站上做得到其實做不到的事（張數、次數、免費範圍）；文中教的方法要和 CTA 打開的工具一致。
19. FAQ 只回答讀者真的會追問的事，每題第一句就答；每一題都會原樣放進畫面和結構化資料。
```

## 模式一：單次生成（中短篇）

```
[system] 你是 {locale} 的網站編輯。只回傳一個 JSON 物件，不用 markdown。所有讀者看得到的文字都用 {locale}。
[user]
標題：{title}｜主關鍵字：{primary_keyword}｜別名：{aliases}
搜尋意圖：{intent}｜核心答案：{core_answer}｜讀者真正的擔心：{reader_worry}

{寫作規則}

動筆前先在心裡確認：這篇的核心答案是什麼？讀者真正在意的是什麼？常見的誤解有哪些？讀完能多做出哪些判斷？

輸出 JSON：
{
 "tldr": "50–90 字的直接答案，一句話，不用問句",
 "description": "50–80 個全形字，說讀完能得到什麼答案，主關鍵字自然出現一次，不抄標題；每個承諾都要對得到正文",
 "intro": ["第一句直接回答…（60–140 字）", "補最常見的情境（60–140 字）"],
 "outline": ["6–8 個 H2；核心答案、怎麼判斷、常見誤解、怎麼做、限制、下一步各一次"],
 "sections": [
  {"heading": "清楚說明這段在做什麼的 H2",
   "paragraphs": ["110–180 字", "110–180 字"],
   "subsections": [{"heading": "具體的 H3（不可寫 heading、標題這類字）", "paragraphs": ["…"]}],
   "bullets": ["選填"],
   "table": {"caption": "表格在比較什麼", "headers": ["…", "…"], "rows": [["…", "…"]]}}
 ],
 "faq": [{"question": "讀者真的會搜、會追問的問題", "answer": "第一句就答（可以，但…／不一定。…），100–180 字"}],
 "keyTakeaways": ["15–45 字，取自正文的結論，不重複描述或 tldr", "…", "…"],
 "cta": {"lead": "按鈕前的一句，24–120 字，有「你／問題／下一步」這類字，不含 8 字以上的標題原句", "button": "只用 {cta_route} 裡的按鈕文字", "condition": "按鈕旁的條件句，照 {cta_route}"},
 "entities": ["0–3 個正文實際談到的實體，不列人名"]
}

站內連結：只能在段落裡用 [[slug:錨文字]]，slug 只能從下列清單挑，錨文字要說清楚那篇在講什麼，全文 3–5 個：
{internal_links}

對手結構觀察（只用來理解結構與涵蓋面，不可照抄）：
{serp_notes}
```

## 模式二：分段生成（長文，建議）

**2-1 先產計畫（不寫正文）**

```
[user]
{title}／{primary_keyword}／{intent}／{core_answer}
{寫作規則}
對手結構觀察（只用來理解結構與涵蓋面，不可照抄）：{serp_notes}
只回傳：{"tldr":"…","description":"…","intro":["…","…"],"articleAngle":"貫穿全文的一句主軸","readerJourney":["讀者從困惑到行動的 3–5 步"],"outline":["6–8 個 H2"],"entities":["…"]}
outline 的每個 H2 任務不同，不可有兩個都在講「怎麼問」；核心答案、怎麼判斷、常見誤解、怎麼做、限制、下一步各一次。
```

**2-2 每次寫 2 個 H2**

```
[user]
只寫指定的 H2 段落，它們是同一篇長文的一部分；不要輸出開頭、FAQ 或參考資料。
{寫作規則}
文章 tldr：{tldr}｜主軸：{articleAngle}｜讀者路徑：{readerJourney}
完整大綱與每段任務：{outline_with_roles}
已完成的 H2：{done_headings}
前文摘要（維持連貫，不要重新開場、不要重複框架）：{previous_summary}
這一批要寫的 H2（照原字，照順序，剛好 {n} 段）：{batch_headings}
回傳：{"sections":[{"heading":"…","paragraphs":["…","…"],"subsections":[{"heading":"…","paragraphs":["…"]}],"table":{…選填}}]}
每個 H2 至少 2 段（每段 110–180 字）、至少 1 個 H3；這一批至少放 1 個站內連結 [[slug:錨文字]]（只能在段落裡）。
可用站內連結：{internal_links}
```

**2-3 最後寫 FAQ、重點與 CTA**

```
[user]
只寫 FAQ、重點與 CTA。{寫作規則}
大綱：{outline}｜正文摘要：{sections_summary}
回傳：{"faq":[{"question":"…","answer":"…"}],"keyTakeaways":["…","…","…"],"cta":{"lead":"…","button":"…","condition":"…"}}
FAQ 剛好 5 題，回答 100–180 字，第一句就答，處理正文沒講完的追問；不寫泛用題。
keyTakeaways 剛好 3 條，每條 15–45 字，取自正文，不可重複描述或 tldr。
cta 的規則同模式一。
```

## 模式三：重寫既有頁（保留網址）

```
[user]
你要整篇重寫一個已上線、網址不變的頁面。
原文（只用來理解現況與可保留的好段落）：{existing_text}
這一頁目前在接的查詢詞（要自然寫進標題、H2 或 FAQ）：{queries_to_keep}
要從即將轉址進來的頁搬入的段落：{merged_sections}
審稿指出的問題（全部要解決）：{review_issues}
{寫作規則}
輸出格式同模式一；另加 "title"（不含品牌的標題文字；加上尾端品牌「{brand}」後合計 ≤32 個全形字，英文約 60 字元；前 12 字放主要意圖詞；原標題準確可讀就保留原字）。
不要刪掉原文中正確、具體、在排名的段落；要刪的只有錯誤、模板、灌水、重複。
```

## 產出後的清洗（你自己做，不交給模型）

- 刪佔位字（`heading`、「段落 1」）、描述文章本身的句子（本文將、讓我們一起、希望這篇…）。
- 掃 AI 殘留與 brief 外洩：`<context>` 這類標籤；「插入實例：」「結合外部資料重點」「本文規劃將回答」「在○○分類下」這類指令；brief 的受眾設定（例：「25 至 38 歲的女性」）。
- 掃相對時間（「今年只剩」「本月」）與標題層的假人設、保證字樣（「專家告訴你」「真實經驗」「一定」）。
- `[[slug:錨文字]]` 只在段落內、且 slug 存在、沒有轉址時才轉成連結；否則只留錨文字。
- 表格 2–5 欄；FAQ ≤6 題，畫面和 FAQPage 結構化資料用同一份清單；實體 ≤3 且不列人名；不輸出參考資料。
- CTA 照 `07` 第 8 節的條件驗證（24–120 字、不含 8 字以上的標題原句、沒有站上不存在的功能名、有「你／問題／下一步」這類字），不合格就改用路由表的規則版文案；再實點一次，確認點下去就能開始。
- 簡轉繁（或你的語系轉換），再跑 `node scripts/content-audit.mjs`。
- 「重點摘要」只有在 3 條都通過（10–60 字、與描述相似度 <0.5、與 tldr／標題 <0.6、彼此 <0.6）時才顯示。
- **人工查核**：逐句對照事實表與產品出處；title、描述、結構化資料、圖片 alt 也要查（Google 2026-10-01 的生成式 AI 內容指南要求發布前人工查核這些欄位）。
- 驗收看必備元素是否齊全，不看字數。

## 交付格式（貼給使用者審）

不要只回報「已完成」。存成 `logs/reviews/<日期>-copy-review.md`，並在回覆中依序寫：

1. **第一句總結**：做完什麼、測試是否全過、有沒有 commit 或部署（預設都沒有）。
2. **改了什麼**：每頁一段，含刻意不動的地方與理由、產品說法對照了哪個出處（實際流程、程式、價格頁）。續做別人的工作時，先寫接手時的狀態。
3. **腳本與產生器**：新增或修改的腳本；在暫存複本重跑相關產生器的結果（零變更，或哪些檔會變、為什麼）。
4. **測試**：新增的測試；改了哪些既有測試的預期（逐條寫理由）；結果；失敗項目在改動前的版本是不是也失敗。
5. **新文案全文（請審）**：title、description、H1、開頭、每個小標與內文、FAQ（註明和結構化資料一致）、CTA 按鈕與前後文字、新加的連結與錨文字。不要只貼摘要。
6. **待你決定／要注意**：逐條列，每條附建議；分三類：要你決定的、要你在別的檔套用的（附可以直接貼上的片段）、部署後要追蹤的（指標與日期）。
7. **截圖與檔案**：改前、改後的截圖（390×844 和 1280×800，第一屏加整頁）；主要檔案的完整路徑。

最常漏的是第 3、4 點，以及「要你在別的檔套用的片段」。
