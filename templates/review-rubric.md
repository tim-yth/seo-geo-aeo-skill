# 審稿評分卡（review rubric）

> 給逐篇審稿、單篇審稿、上線前審查共用。判定規則和問題代碼以本檔為準；提示檔 `prompts/site-audit-batch-reviewer.md`、`prompts/content-reviewer.md` 輸出的判定行都使用這裡的代碼。
> 寫作標準的出處與案例數字見 `references/07-content-writing-standard.md`；長度規格以 `references/09-ctr-titles-snippets.md` 第 3 步為準。

## 1. 評等

| 評等 | 判定 | 動作代碼 |
|---|---|---|
| A | 內容好，最多錯字級問題 | `keep` |
| B | 明確但局部的問題（某段錯、FAQ 弱、連結錯、模板殘留） | `fix` |
| C | 骨架可留，但大多空泛、模板化或邏輯差 | `rewrite` |
| D | 跟別頁同意圖，或太薄救不回 | `merge`（給目標）；唯一有排名的頁用 `keep-rewrite`；暫不處理且不想被收錄用 `noindex`（最後手段，見 `08` 決策規則 2 第 17 條） |
| X 旗標 | 有會誤導或不該出現的內容（可疊加在任何評等上） | 依 X 代碼先修 |

判定順序：先找 X → 同意圖已有更好的頁或太薄 → D → 骨架可用但大半空泛 → C → 局部問題 → B → 只剩錯字 → A。

不要為挑錯而挑錯：A 級要寫一行理由，B 以上要寫「優點：值得保留的段落」。

## 2. 檢查面向

| # | 面向 | 通過條件 | 快速檢查 |
|---|---|---|---|
| 1 | 事實 | 實體、編號、結構、產品功能與價格都對；沒有寫出產品沒有的服務型態 | 對照事實表；產品句依真相順序核對：實際流程 > 程式設定 > 價格頁與條款 > 介紹頁 |
| 2 | 前後一致 | 導言、H2、FAQ、CTA 立場一致；界線句沒有勸退產品的核心動作 | 找「不能 X」與「解讀 X」並存的地方；拿舊立場的說法反查小標、表頭、示範、FAQ、描述 |
| 3 | 標題承諾 | 標題說的內文都有 | 「22 張」就數 22 張；「對照表」就找表 |
| 4 | 答案在前 | 前三行回答標題或點出擔心 | 第一句是不是答案；有沒有「本文將」 |
| 5 | 具體 | ≥2 個情境、一次完整示範、該有的表 | 有沒有「例如…」與實際內容 |
| 6 | 意圖重複 | 站內沒有同意圖頁 | 列出同意圖 slug 與建議主文（`.html`／無副檔名是同一頁，不算重複） |
| 7 | 模板／灌水 | 沒有模板句、照抄描述、堆砌、頁首模板外洩 | 重點摘要＝描述？同一內連 ≥3 次？人名 >2 次？頁首有「關鍵字：」或原始時間格式？ |
| 8 | 好讀度 | 段落長度適中、小標有資訊、順序合理 | 小標只是重述？段落換句話重複？超過 60 字的長句多不多？（只當參考，不打分數） |
| 9 | CTA 與內連 | CTA 對題、功能存在、點下去能開始、條件寫在按鈕旁；內連是下一步 | CTA 連同前後兩句讀：讀者以為能做到的事，站上做得到嗎？有沒有塞標題、指向不存在的功能 |
| 10 | 不該寫的（X） | 無 X 類內容（標題層也要掃） | 見第 3 節 |
| 11 | 信任與署名 | 署名誠實、製作方式說得清楚、出處可驗證 | 見下方「信任自查」 |

### 信任自查（E-E-A-T，誠實版）

- **署名**：讀者會預期看到作者的頁（教學、評測、比較）有署名。品牌編輯部署名時，連得到「關於我們／內容製作方式」頁；具名作者要有作者頁（經歷、專長、聯絡方式）才標 Person；AI 角色不標 Person。捏造作者（AI 頭像、假名、假資歷）→ `fake_expert`。
- **製作方式**：主要由 AI 產生的內容，在讀者會問「這是怎麼做出來的？」的地方說明 AI 參與與人工查核。整站還沒有揭露方式時，整站列一條 `decide`，不要每篇各列。
- **人工查核**：AI 產出的 title、描述、結構化資料、圖片 alt 都查核過；錯的依內容列對應代碼。
- **證據**：示範可以重現（工具頁範例結果用正式流程產生、只裁不改）；參考資料可驗證、跟主題相關，不是搜尋結果頁、消歧義頁或另一主題的條目 → 不符列 `bad_links`；生成的參考資料 → `fake_expert`。
- **事實與產品**：照真相順序核對；情境錯置 → `wrong_product_claim`。
- **為讀者而寫**：只為接住某個關鍵字變體而存在的頁 → `duplicate_intent` 或 `thin`。

## 4. 一般問題代碼

| 代碼 | 意思 |
|---|---|
| `no_answer_first` | 前三行沒有回答，或以「本文將…」開場 |
| `promise_unmet` | 標題或描述承諾的內容沒有兌現 |
| `contradiction` | 自相矛盾（含修一半產生的新矛盾；界線句勸退產品的核心動作） |
| `duplicate_intent` | 與站內其他頁同意圖 |
| `thin` | 內容太薄 |
| `template` | 模板句、重點摘要照抄描述、套模板 CTA 或延伸閱讀；頁首模板外洩（內部欄位、原始時間格式、和內容不符的閱讀時間或篇數） |
| `stuffing` | 關鍵字、人名堆砌，或同一內連重複 |
| `vague` | 空泛：沒有情境、沒有示範 |
| `missing_table` | 該用表格卻沒有 |
| `weak_faq` | FAQ 泛用、答非所問、第一句沒答；為了搜尋版面硬加的題目 |
| `cta_mismatch` | CTA 不對題、塞標題、指向不存在的功能、點下去不能開始、和前後文字一起讀會讓人誤會（例：以為能抽 36 張、以為五次都免費）、方法和工具不一致 |
| `bad_links` | 內連不相干、目標錯、經過轉址；參考資料連到搜尋結果頁、消歧義頁、另一主題的條目 |
| `schema_mismatch` | 結構化資料與畫面不一致、JSON 無法解析、隱藏欄位沒跟著內容改（citation、about、wordCount） |
| `title_meta` | 標題或描述超出 `09` 的長度規格、誇大、模板後綴、不通順 |
| `terminology` | 用詞不一致、地區用語、繁簡殘字、用字與標點（反饋、“ ”、半形問號、你／妳混用） |
| `readability` | 段落太長太碎、順序亂、長句堆疊、語氣不像人 |
| `mobile_layout` | 手機版面問題：5 欄以上或含長英數字串的表撐破版面、表格沒包捲動容器、窄欄每行只剩幾個字 |
| `outdated` | 過期年份或過期資訊；寫死當下的相對時間（「今年只剩…」）、綁月份的標題、頁首更新日比內文舊 |

嚴重度：`x`（X 類）｜`must_fix`（上線前必修）｜`should_fix`（可下一輪）｜`decide`（需要使用者決定）。

**`schema_mismatch` 分級：**

- `must_fix`（上線門檻）：結構化資料裡有畫面上找不到的題目或答案；JSON 無法解析；結構化資料標示了畫面上已經刪掉的出處或人名（citation、about）。
- `must_fix`：新寫或重寫的頁，FAQ 的題數、題目、答案、順序沒有完全一致。
- `should_fix`：既有模板的頁差一題，但每一題都在畫面上（例：畫面 6 題、結構化資料 5 題），交給產生器補齊；wordCount、閱讀時間沒跟著重寫更新。

**`decide` 常見的 8 類**。列給使用者時，每條都附預設建議，讓對方只要回「照建議」就好：

| 代號（`decide_type`） | 類型 | 例 | 預設建議 |
|---|---|---|---|
| `title_sync` | 會動到標題、要全站同步 | 誘餌標題；標題壞掉（雙冒號、整串搜尋字、大綱殘段） | 排進解凍後同一批標題傳播；觀察中的頁不動 |
| `thin_page` | 空殼或極薄頁 | 正文只有一句 CTA，卻開放索引 | 有主文就提前 301；沒有就先 noindex |
| `main_swap` | 換主文或換網址 | 要不要拿排前 3 名的網址去換；D 級網址要不要換內容不換網址 | 不拿前 3 名去換；優先換內容、不換網址 |
| `term_choice` | 術語統一 | 兩種譯名都有人搜 | 跟正式實體頁和主要查詢詞一致，另一種在內文註明 |
| `product_gap` | 產品面不一致 | 介紹頁寫了程式沒有的功能；CTA 目標頁的按鈕只回首頁；CTA 路由表沒有合適的去處 | 交給產品決定；文章先照實際流程寫，不自己發明去處 |
| `standard_gray` | 標準本身的灰色地帶 | 比較文寫「情緒很重時找真人比較適合」；主題本身需要的人名超過上限；整站還沒有 AI 參與的揭露方式 | 沒有貶低、也沒有吹捧就放行，並寫進標準當例外 |
| `unverifiable` | 無法自動驗證的事實 | 參考資料網站擋自動存取 | 請使用者開瀏覽器確認；不符就把畫面和結構化資料一起刪 |
| `out_of_scope` | 超出本回合範圍的大改 | B 級文章有四成篇幅離題 | 升成 C 級重寫，或只刪離題段 |

## 5. 人看的評分卡（每篇一段）

```markdown
### <slug>
- 評等：C+X
- 標題：<TITLE>
- 主要問題：
  1. [fake_expert] 虛構資歷與個案：「以我多年解牌的經驗來看…」
  2. [promise_unmet] 標題「22 張完整解析」，內文只講 8 張
  3. [template] 「重點摘要」與 meta 描述一字不差
- 建議修法：刪假資歷段；補 22 張速查表；重點摘要改成正文 3 個結論；或 301 到 <slug>（先搬「愚者之旅」段）
- 優點：「三階段」框架清楚，可保留
```

## 6. 機器判定行（每篇必附，供腳本合併）

規則：每行以大寫標籤開頭、後面接一個空格和一個「單行 JSON」；不要放在程式碼區塊或清單符號後面；字串裡引用原文用「」，不要用 ASCII 雙引號；沒有值用空字串或空陣列。

```
VERDICT {"slug":"<slug>","grade":"C","x":["fake_expert"],"action":"rewrite","target":"","dup_of":[],"move":"","note":"一句話理由"}
ISSUE {"slug":"<slug>","severity":"x","code":"fake_expert","where":"intro","quote":"以我多年解牌的經驗來看","fix":"刪除，改成「例如：如果你抽到…」"}
ISSUE {"slug":"<slug>","severity":"decide","decide_type":"title_sync","code":"title_meta","where":"title","quote":"真相大公開！他現在到底怎麼想","fix":"建議：排進解凍後同一批標題傳播"}
```

- `grade`：`A`｜`B`｜`C`｜`D`
- `x`：第 3 節代碼的陣列
- `action`：`keep`｜`fix`｜`rewrite`｜`merge`｜`keep-rewrite`｜`noindex`
- `target`：`merge` 時填目標網址或 slug
- `dup_of`：同意圖的 slug（正規化後的網址；同一篇的 `.html` 與無副檔名版不列）
- `move`：轉址前要搬進主文的段落
- `where`：`title`｜`meta`｜`h1`｜`header`（頁首：麵包屑下的關鍵字列、日期、閱讀時間）｜`intro`｜`h2:<小標文字>`｜`faq:<題號>`｜`cta`｜`related`｜`schema`｜`table`｜`body`
- `decide_type`：只在 `severity` 是 `decide` 時加，值見第 4 節的 8 個代號；其他 ISSUE 行不用加

## 7. 範例（SaaS 功能頁）

```markdown
### invoice-auto-reconciliation
- 評等：B
- 主要問題：
  1. [no_answer_first] 前兩段在講公司願景，第三段才說能不能自動對帳
  2. [wrong_product_claim] 寫「所有銀行都支援」，設定頁只列 12 家
- 建議修法：第一句改成「可以，但只限已串接的銀行帳戶」；補支援銀行表
- 優點：跨幣別收款的操作步驟清楚
VERDICT {"slug":"invoice-auto-reconciliation","grade":"B","x":["wrong_product_claim"],"action":"fix","target":"","dup_of":[],"move":"","note":"答案在第三段；支援銀行說法過頭"}
```
